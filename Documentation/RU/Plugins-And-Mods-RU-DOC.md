# 🧩 IceBox Engine — Плагины и Моды

## Полная документация на русском языке

> **IceBox Engine** расширяется двумя взаимодополняющими способами:
>
> * **Плагины** — нативные **C++**-модули, расширяющие **редактор** и/или **рантайм**
>   через стабильный C-ABI. Используйте их для добавления панелей, инструментов, пунктов
>   меню, кастомных типов ассетов, кнопок тулбара, оверлеев вьюпорта, страниц настроек,
>   нод Visual Script и интеграций с внешними сервисами.
> * **Моды** — бандлы **Lua + контент**, загружаемые во время выполнения. Используйте их
>   для добавления или изменения геймплея и поставки новых ассетов (спрайтов,
>   классов, виджетов, …) без правки базовой игры и без перекомпиляции.
>
> Этот документ объясняет, как работают обе системы, как их включать и управлять ими, и
> как **создавать собственные** плагины и моды с нуля.
>
> Сами языки/API Lua и Python описаны отдельно в
> [LuaAPI-RU-DOC.md](LuaAPI-RU-DOC.md) и [PythonAPI-RU-DOC.md](PythonAPI-RU-DOC.md).
> О типах ассетов, которые поставляет мод, см. [Ассеты и Браузер контента](Assets-RU-DOC.md);
> о том, как плагины/моды упаковываются в релизную сборку, см.

## 1. Введение

Обе системы расширения управляются единой подсистемой движка (**менеджер плагинов**,
Plugin Manager) и доступны через единую панель редактора (**Plugins & Mods**), но это
очень разные инструменты:

* **Плагин** — это скомпилированный нативный код. Он линкуется с **Plugin SDK** движка,
  реализует интерфейс `IPlugin` и загружается как разделяемая библиотека
  (`.dll` / `.so` / `.dylib`) — или линкуется статически на платформах без динамической
  загрузки. Плагины могут глубоко проникать в редактор и рантайм через host API.
* **Мод** — это папка с Lua и контентом. Его входной скрипт выполняется в песочничной
  среде Lua с доступными глобалами движка; он может спавнить поставляемые им классы,
  виджеты и ассеты и встраиваться в жизненный цикл уровня. Компилятор не нужен.

Обе системы живут в собственных корневых папках — `Plugins/` и `Mods/` — и обе включаются
для проекта через небольшие JSON-файлы конфигурации.

Движок поставляет по одному эталонному примеру каждого вида:

* **`Plugins/AIHelper`** — нативный плагин редактора, добавляющий *Инструменты → AI Helper*,
  панель чата, подключённую к локальной LLM Ollama. Он индексирует все языковые папки
  внутри `Documentation/`, каталог API скриптинга из `Config/VisualScriptAPI.json`,
  README-файлы проекта и, по желанию, ваши собственные исходники на Lua/Python, после
  чего подбирает наиболее релевантные разделы под каждый вопрос. Роль, стиль ответа,
  сэмплирование, поиск по документации и интерфейс настраиваются прямо в панели и
  сохраняются в `Config/AIHelper.json`; сохранённые диалоги лежат в `Saved/AIHelper/`.
  См. [`Plugins/AIHelper/README.md`](../../Plugins/AIHelper/README.md).
* **`Mods/PlatformerCrates`** — Lua-мод, добавляющий собираемые ящики и счётчик-HUD в
  пример Platformer, поставляющий собственные классы, виджет и спрайт. См.
  [`Mods/PlatformerCrates/README.md`](../../Mods/PlatformerCrates/README.md).

## 2. Плагины vs Моды — что выбрать?

| | **Плагины** | **Моды** |
| --- | ----------- | -------- |
| **Язык** | C++ (компилируется) | Lua + контент (интерпретируется) |
| **В основном расширяет** | Редактор **и** рантайм (глубоко, нативно) | Геймплей рантайма + поставляет ассеты |
| **Манифест** | `plugin.json` | `mod.json` |
| **Точка входа** | `CreatePlugin()` → `IPlugin` | `main.lua` (входной скрипт) |
| **Нужна сборка?** | Да — CMake, поставляется как библиотека (или статически) | Нет — поставляется как есть |
| **Папка** | `Plugins/<Name>/` | `Mods/<Name>/` |
| **Конфиг** | `Config/Plugins.json` | `Config/Mods.json` |
| **Работает в редакторе?** | Да — ради этого редакторские плагины и существуют | Нет — моды работают только в Play-режиме / в игре |
| **Переключение без перезапуска?** | Да, если библиотека уже собрана (см. [5.1](#51-панель-plugins--mods)) | Да — включаются/выключаются и обновляются «на лету» |
| **В песочнице?** | Нет (нативный код, полная мощь) | Да (своя среда Lua) |
| **Версионирование** | Версия C-ABI (`ICE_PLUGIN_API_VERSION`) | `APIVersion` мода |
| **Типичное применение** | Новые панели/инструменты, кастомные типы ассетов, пункты меню/тулбара, оверлеи вьюпорта, ноды Visual Script, внешние интеграции | Новые уровни/механики/контент, тотальные конверсии, правки геймплея |

**Правило большого пальца:** если нужны новые **инструменты редактора** или нативная
производительность/интеграция — пишите **плагин**. Если хотите добавить или изменить
**игровой контент и поведение** скриптами — пишите **мод**.

# Часть I — Плагины (нативный C++)

## 3. Система плагинов

Плагин — это нативный модуль, реализующий `IceBox::IPlugin` (объявлен в
`PluginInterface.h`) и собираемый с CMake-таргетом **`IceBoxPluginSDK`**. Движок находит
его в `Plugins/<Name>/`, загружает при включении и вызывает через набор хуков жизненного
цикла. В ответ плагин обращается к движку через версионированный **host API**.

### 3.1 Что может плагин

Через host API редактора плагин может, среди прочего:

* **Регистрировать новый UI редактора** — пристыковываемые панели, пункты меню **Tools**,
  кнопки тулбара, оверлеи вьюпорта, пункты контекстного меню вьюпорта/сущности и страницы
  настроек.
* **Регистрировать кастомные типы ассетов** — новое `.ext` со своей иконкой, цветом,
  отображаемым именем и обработчиками *open/create*, интегрирующимися в Браузер контента.
* **Управлять сценой** — создавать/дублировать/удалять сущности, читать и задавать
  трансформации, добавлять и удалять компоненты, инстанцировать классы,
  импортировать/экспортировать JSON сущностей.
* **Управлять редактором** — выделение, камера/вьюпорт, undo/redo, play/stop,
  сохранение/загрузка сцен, открытие ассетов, показ/скрытие панелей, логирование и
  уведомления.
* **Привязывать скриптинг** — регистрировать функции в каждом Lua-состоянии и/или в
  модуле Python редактора.
* **Реагировать на события** — принимать события редактора/движка и выполнять логику
  каждый кадр рантайма и при старте/остановке play.
* **Поставлять данные** — упаковывать собственные папки контента и `VisualScriptAPI.json`,
  добавляющий ноды в редактор Visual Script (см.
  [3.12](#312-поставка-данных-и-нод-visual-script-вместе-с-плагином)).

### 3.2 Анатомия плагина

Плагин — это папка в `Plugins/`:

```
Plugins/MyPlugin/
    plugin.json           # манифест (имя, версия, иконка, зависимости …)
    CMakeLists.txt        # сборка плагина с IceBoxPluginSDK
    Source/
        MyPlugin.cpp      # ваш наследник IPlugin + ICE_PLUGIN_ENTRY(...)
        ...               # любые другие исходники/заголовки
    Icon.png              # опциональная иконка в панели Plugins
    README.md             # опционально; индексируется плагином AI Helper
    VisualScriptAPI.json  # опционально; дополнительные ноды Visual Script
    Content/  Assets/  Scripts/  Lua/    # опциональные папки данных
```

После сборки скомпилированная библиотека и копия `plugin.json` попадают в выходную папку
плагинов движка (`bin/<platform>/Plugins/MyPlugin/`), откуда движок их и загружает. На
Android библиотека вместо этого кладётся в `lib/Android/<ABI>/`; при статической сборке
(Web, iOS) она линкуется прямо в исполняемый файл рантайма.

### 3.3 Манифест `plugin.json`

Небольшой JSON-файл, описывающий плагин:

```json
{
    "Name": "MyPlugin",
    "Description": "Adds a Hello panel to the editor.",
    "Author": "You",
    "Version": "1.0.0",
    "Icon": "Icon.png",
    "EditorOnly": true,
    "Dependencies": []
}
```

| Поле | Значение | По умолчанию |
| ---- | -------- | ------------ |
| `Name` | Уникальное имя плагина (должно совпадать с тем, что включается в `Plugins.json`). | имя папки |
| `Description` | Показывается в панели Plugins. | `""` |
| `Author` | Показывается в панели Plugins. | `""` |
| `Version` | Отображаемая строка версии. | `"1.0.0"` |
| `Icon` | Путь (относительно папки плагина) к иконке `.png` / `.jpg` / `.jpeg`. | автоопределение |
| `EditorOnly` | `true` помечает плагин как **чисто редакторский**: он никогда не компилируется в игру, не попадает в сборку и не загружается игрой ни на одной платформе. | `false` |
| `Dependencies` | Имена других плагинов, которые должны загрузиться первыми. | `[]` |

> **`EditorOnly` — это жёсткая граница между инструментами и поставкой.** Плагин с этим
> флагом пропускается CMake во всех рантайм-конфигурациях (desktop, Android, Web, iOS),
> никогда не копируется и не накладывается в вывод сборки, и отклоняется Plugin Manager,
> если каким-то образом всё же попал в игру. Ставьте его всему, что рисует ImGui
> редактора, обращается к `EditorHostAPI` или не имеет смысла в рантайме — так сделан
> встроенный `AIHelper`. Плагинам, у которых редакторская часть опциональна, оставляйте
> `false`.

> **Разрешение иконки.** Если `Icon` отсутствует, пуст, указывает не на изображение или
> на несуществующий файл, движок переходит к автоопределению и ищет в папке плагина
> `icon.png`, `icon.jpg`, `icon.jpeg`, `Icon.png`, `Icon.jpg`, `Icon.jpeg` — именно в
> этом порядке. Если иконки нет вовсе, панель рисует серый квадрат со знаком `?`.

> Авторитетные `Name`, `Version` и **версия API** также берутся из `GetPluginInfo()`
> плагина при загрузке; манифест — это то, что редактор показывает до загрузки.

### 3.4 Интерфейс `IPlugin` и жизненный цикл

Ваш плагин наследует `IceBox::IPlugin` и переопределяет нужные хуки. Обязательны только
первые три. Колонка **Мин. API** — это значение `PluginInfo::APIVersion`, которое плагин
должен сообщить, чтобы движок вообще диспатчил ему этот хук (см.
[3.9](#39-версионирование-api--abi)).

| Хук | Мин. API | Когда вызывается |
| --- | :------: | ---------------- |
| `PluginInfo GetPluginInfo() const` | — | Идентифицировать плагин (имя, описание, автор, версия, **APIVersion**). **Обязателен.** |
| `bool OnLoad()` | — | Плагин загружен. Верните `false`, чтобы прервать загрузку. **Обязателен.** |
| `void OnUnload()` | — | Плагин выгружается. **Обязателен.** |
| `void OnUpdate(float dt)` | — | Каждый кадр **рантайма** — то есть пока идёт игра или Play-режим. Он **не** тикает, пока редактор просто простаивает; для покадровой работы в редакторе используйте `OnEditorUI`. |
| `void OnRuntimeStart()` / `OnRuntimeStop()` | — | Play-режим / игра запущены или остановлены. |
| `void OnEditorInit(const EditorPluginContext&)` | — | Готов **редакторский** host (даёт вам контекст ImGui). |
| `void OnEditorShutdown()` | — | Редактор завершает редакторскую часть плагина (вызывается и прямо перед выгрузкой). |
| `void OnEditorToolsMenu()` | — | Добавить пункты в меню **Tools** редактора (рисуйте `ImGui::MenuItem`). |
| `void OnEditorUI(float dt)` | — | Рисовать свой ImGui каждый кадр редактора (панели, окна). |
| `void OnRegisterLua(void* L)` / `OnUnregisterLua(void* L)` | 3 | Создано/уничтожено Lua-состояние — привязать/отвязать ваши Lua-функции. |
| `void OnEngineInit(const PluginRuntimeContext&)` | 4 | Сразу после `OnLoad`, передаёт вам `RuntimeHostAPI`. Диспатчится **и в редакторе, и в отдельном рантайме** — это не хук «только для процесса игры». |
| `void OnRegisterPython(void* module)` | 4 | Зарегистрировать привязки в модуле Python редактора. |
| `void OnEditorEvent(const char* name, const char* payload)` | 4 | Отправлено событие редактора. |
| `void OnEngineEvent(const char* name, const char* payload)` | 4 | Отправлено событие рантайма/движка. |

Плагин может быть **только редакторским** (реализует только хуки `OnEditor*`), **только
рантайм** (реализует `OnEngineInit`/`OnUpdate`/`OnRuntime*`) или обоими.

**Какие Lua-состояния вам достанутся.** `OnRegisterLua` вызывается для каждого
Lua-состояния, которое создаёт движок, и для всех уже существующих состояний в момент
загрузки плагина: это основное состояние геймплея/скриптов и отдельное состояние
**widget runtime**, используемое интерфейсами `.ice_widget`. Регистрируйте свои функции в
каждом переданном `L` и отменяйте это в `OnUnregisterLua`.

**Какой модуль Python вам достанется.** `OnRegisterPython` получает `pybind11::module_*`,
указывающий на модуль `__main__` редактора — тот самый, где живут встроенные привязки
`editor`, `scene`, `engine` и `browser`.

**Какие события вам придут.** `OnEditorEvent` срабатывает на каждое событие, поднятое
через `FireEvent(...)` из Python редактора; payload сейчас всегда `nullptr`.
`OnEngineEvent` срабатывает с `"runtime_started"` и `"runtime_stopped"` вокруг
Play-режима. Учтите: `RuntimeHostAPI::FireEvent` эмитит **Lua**-событие для
скриптов-слушателей и не приводит к повторному вызову `OnEngineEvent`.

> **Исключения не «убивают» редактор.** Каждый хук, который диспатчит менеджер, обёрнут в
> `try/catch`; бросивший плагин логируется (`Plugin '<name>' <hook> threw: …`), а
> остальные продолжают работать. Но бросать исключения через границу ABI всё равно нельзя.

### 3.5 Host API — обращение к движку

Контексты, передаваемые вашему плагину (Раздел [3.7](#37-контексты-плагина-и-imgui)),
несут указатель на host API — обычную C-структуру указателей на функции — плюс
непрозрачный хэндл `HostContext`, который вы передаёте первым аргументом в каждый вызов.
Обе структуры начинаются с `StructSize` и `AbiVersion`, так что вы можете проверить, что
именно вам передали.

**`EditorHostAPI`** (редактор) предоставляет, среди многого прочего:

* **Логирование / UX:** `Log`, `Notify`. Обе принимают уровень: `0` — trace, `1` — info,
  `2` — warning, `3` — error; сообщения попадают в **Консоль** редактора.
* **Выделение:** `EnumSelectedEntities`, `GetPrimarySelected`, `SetSelection`,
  `SelectEntity`, `ClearSelection`, `SelectAll`.
* **Сущности:** `EnumAllEntities`, `GetEntityCount`, `CreateEntity`, `InstantiateClass`,
  `DuplicateEntity`, `DeleteEntity`, `EntityExists`, `FindEntityByName`,
  `Get/SetEntityName`, `Export/ImportEntityJson`.
* **Трансформации:** `Get/SetPosition`, `Get/SetScale`, `Get/SetRotation`, `Translate`.
* **Компоненты:** `HasComponent`, `AddComponent`, `RemoveComponent`, `EnumComponentTypes`.
* **Сцена:** `GetScenePath`, `SaveScene`, `LoadScene`, `NewScene`, `MarkSceneDirty`,
  `IsSceneDirty`.
* **Ассеты / браузер:** `OpenAsset`, `RefreshContentBrowser`, `GetContentBrowserPath`.
* **Вьюпорт / камера:** `GetViewportSize`, `ScreenToWorld`, `IsViewportHovered`,
  `IsViewportFocused`, `Get/SetCamera`, `FocusEntity`.
* **Управление редактором:** `RecordUndo`, `Undo`, `Redo`, `IsPlayMode`, `Play`, `Stop`,
  `Set/IsPanelVisible`.
* **Регистрация:** см. [Раздел 3.6](#36-точки-расширения-редактора).

Функции, возвращающие текст (`GetEntityName`, `GetScenePath`, `ExportEntityJson`,
`GetContentBrowserPath`, …), следуют обычной C-конвенции: они пишут не более
`bufSize - 1` байт плюс терминатор и возвращают **требуемую** длину — так что можно
вызвать их один раз с маленьким буфером, чтобы узнать нужный размер.

`Set/IsPanelVisible` принимают одно из имён панелей редактора:
`Hierarchy`, `Properties`, `Stats`, `ContentBrowser`, `Settings`, `NetworkPanel`,
`Profiler`, `WorldSettings`, `HotKeys`, `Documentation`, `LuaDebugger`, `Plugins`,
`Console`, `PythonConsole`, `About`, `PropertyMatrix`, `LevelScriptEditor`,
`TextNoteEditor`, `RemotePreview`, `BuildGame`, `DLCPackager`. Панели редакторов ассетов
(`ClassEditor`, `SpriteEditor`, `MaterialEditor`, …) так можно только **закрыть** —
открывать их следует через `OpenAsset`.

**`RuntimeHostAPI`** (рантайм) предоставляет: `Log`, `GetEngineRoot`, `IsPlaying`,
`GetTime`, `HasScene`, `EnumEntities`, `GetEntityName`, `GetConfigString` /
`SetConfigString`, `FireEvent` и `GetLuaState`. `GetConfigString`/`SetConfigString` — это
простое key/value-хранилище в памяти, общее для всех рантайм-плагинов; `FireEvent`
эмитит Lua-событие, которое получают слушатели `On("name", handler)`.

### 3.6 Точки расширения редактора

Эти функции `EditorHostAPI` позволяют плагину добавлять полноценные возможности
редактора. Вызывайте их из `OnEditorInit` (или позже) — они доступны только в сборках с
редактором.

| Функция | Добавляет | Где появляется |
| ------- | --------- | -------------- |
| `RegisterPanel(id, title, render, user)` | Пристыковываемую панель; возвращает id панели для `ShowPanel`/`IsPanelOpen` (`0` — регистрация не удалась). | Отмечаемый пункт внизу меню **Window**; само окно называется `title`, при первом открытии 480×360, а ваш `render(bool* pOpen, user)` рисует внутри него. |
| `RegisterAssetType(const IceAssetTypeDesc*)` | Кастомный тип ассета — расширение, отображаемое имя, текст и цвет иконки, колбэки `OnOpen`/`OnCreate`. | Браузер контента: текст и цвет значка, имя типа для этого расширения, пункт вверху контекстного меню **создания** на пустом месте (только если задан `OnCreate`) и обработка двойного клика через `OnOpen`. |
| `RegisterMenuItem(menuPath, shortcut, cb, user)` | Пункт меню. | Меню **Tools**, ниже встроенных пунктов. `menuPath` без `/` даёт плоский пункт; `Group/Item` кладёт `Item` в подменю `Group`. |
| `RegisterToolbarButton(id, tooltip, cb, user)` | Кнопку тулбара. | Основной тулбар, после встроенных кнопок. `id` — это видимая надпись, `tooltip` — подсказка при наведении. |
| `RegisterViewportOverlay(cb, user)` | Колбэк отрисовки. | Вызывается последним внутри окна вьюпорта каждый кадр, так что `ImGui::GetWindowDrawList()` рисует поверх сцены. |
| `RegisterContextMenuItem(context, label, cb, user)` | Пункт контекстного меню. | Меню правого клика во вьюпорте. `context` должен быть `"viewport"` (показывается всегда) или `"entity"` (только когда выделена хотя бы одна сущность). |
| `RegisterSettingsPage(category, cb, user)` | Страницу настроек. | Вкладка **Settings** панели Plugins & Mods, в виде сворачиваемого заголовка с именем `category`. Сама вкладка появляется, только когда зарегистрирована хотя бы одна страница. |

Примечания:

* **`IceAssetTypeDesc`** содержит `StructSize`, `Extension` (движок сам приводит его к
  нижнему регистру), `DisplayName`, `IconText`, `IconColor[4]`, `OnOpen`, `OnCreate` и
  `User`. `OnCreate` получает **текущую папку** браузера контента, `OnOpen` — **путь к
  ассету**. Встроенные расширения движка всегда в приоритете, поэтому переоформить
  `.ice_class` и подобные не выйдет; если два плагина заявляют одно расширение, побеждает
  **последняя** регистрация.
* **Выгрузка всё убирает.** Когда плагин выгружается (или отключается), все
  зарегистрированные им панели, типы ассетов, пункты меню, кнопки тулбара, оверлеи,
  контекстные пункты и страницы настроек снимаются автоматически — снимать их вручную не
  нужно.
* `RegisterAssetType` — это способ для плагинов вводить совершенно новые виды ассетов;
  Браузер контента запрашивает у зарегистрированных типов иконку, цвет и пункт меню
  создания — см. [Ассеты и Браузер контента](Assets-RU-DOC.md).

### 3.7 Контексты плагина и ImGui

При инициализации движок передаёт вашему плагину структуру контекста:

* **`EditorPluginContext`** (в `OnEditorInit`) — содержит `ImGuiContext*` редактора и
  функции аллокатора ImGui, путь к корню движка, путь к папке этого плагина, функцию
  `Log` и `EditorHostAPI* Host` + `HostContext`.
* **`PluginRuntimeContext`** (в `OnEngineInit`) — путь к корню движка, путь к папке
  плагина, `Log` и `RuntimeHostAPI* Host` + `HostContext`.

`PluginFolderPath` всегда использует прямые слеши и является правильной базой для
загрузки собственных файлов данных; `EngineRootPath` — рабочий каталог движка.

**Отрисовка ImGui через границу DLL.** Поскольку плагин — это отдельный бинарник со своим
ImGui, перед отрисовкой нужно перенять контекст и аллокатор ImGui хоста — сделайте это
один раз в `OnEditorInit`:

```cpp
void OnEditorInit(const IceBox::EditorPluginContext& ctx) override {
    m_Ctx = ctx;
    if (ctx.ImGuiCtx) ImGui::SetCurrentContext(ctx.ImGuiCtx);
    if (ctx.ImGuiAllocFn && ctx.ImGuiFreeFn)
        ImGui::SetAllocatorFunctions(ctx.ImGuiAllocFn, ctx.ImGuiFreeFn, ctx.ImGuiUserData);
}
```

После этого ваши `OnEditorToolsMenu` и `OnEditorUI` могут вызывать ImGui как обычно, и
ваши виджеты отрисуются внутри редактора.

### 3.8 Точки входа: динамическая vs статическая

Плагин экспонирует пару фабрик, `CreatePlugin()` / `DestroyPlugin()`. Макрос
`ICE_PLUGIN_ENTRY(MyPluginClass)` генерирует их за вас:

```cpp
ICE_PLUGIN_ENTRY(MyPlugin)   // на уровне файла, после определения класса
```

* **Динамическая (по умолчанию)** — на десктопе это экспортирует
  `CreatePlugin`/`DestroyPlugin` из разделяемой библиотеки; движок выполняет
  `dlopen`/`LoadLibrary` и разрешает символы. Загрузчик берёт **первый** найденный в
  папке плагина `.dll` (Windows) или `.so`/`.dylib` (Unix), поэтому держите по одной
  библиотеке на папку.
* **Статическая** — на платформах без динамической загрузки (**Web**, **iOS**) или при
  вашем явном выборе движок собирает плагины с `ICE_PLUGIN_STATIC_BUILD`. Тот же макрос
  тогда **регистрирует плагин в статическом реестре** при старте, и движок линкует его
  прямо в рантайм с whole-archive-линковкой. (Можно зарегистрировать и явно через
  `ICE_PLUGIN_REGISTER_STATIC(Name, Class)`.)
* **Android** — гибрид: Gradle кладёт `.so` плагинов в `nativeLibraryDir` внутри APK,
  поэтому, если рядом с `plugin.json` библиотека не найдена, загрузчик пробует
  `dlopen("lib<Name>.so")` по санированному имени плагина, а затем откатывается к
  статическому реестру.

Статически зарегистрированные плагины, у которых нет папки на диске, всё равно
обнаруживаются — менеджер синтезирует запись с именем регистрации, так что её можно
включать в `Plugins.json` как любой другой плагин.

Код вашего плагина одинаков во всех режимах — макрос обрабатывает разницу, управляемую
переменной CMake `ICE_PLUGIN_BUILD_STATIC`.

### 3.9 Версионирование API / ABI

ABI плагинов версионируется через `IceBox::ICE_PLUGIN_API_VERSION` (сейчас **4**). Ваш
плагин сообщает версию, под которую он собран, в `PluginInfo::APIVersion` (задайте её
равной `ICE_PLUGIN_API_VERSION`).

* Если `APIVersion` плагина **больше**, чем у движка, движок **отказывается его
  загружать** (он собран под более новый ABI) и пишет в лог
  `Plugin '<name>' requires API version N (engine has 4)`.
* Новые хуки/возможности гейтятся по версии внутри, так что старые плагины продолжают
  работать по мере роста ABI:

| Версия | Что появилось |
| :----: | ------------- |
| ≤ 2 | Базовый жизненный цикл: `GetPluginInfo`, `OnLoad`, `OnUnload`, `OnUpdate`, `OnRuntimeStart/Stop` и все хуки `OnEditor*`. |
| 3 | `OnRegisterLua` / `OnUnregisterLua`. |
| 4 | `OnEngineInit` (а значит и `RuntimeHostAPI`), `OnRegisterPython`, `OnEditorEvent`, `OnEngineEvent`. |

Всегда пересобирайте плагины под версию движка, с которой поставляетесь.

### 3.10 Файл `CMakeLists.txt` плагина

У каждой папки плагина есть `CMakeLists.txt`. Именно его компилирует
[Plugin Builder](#313-сборка-плагина--plugin-builder), когда вы собираете плагин, и
именно его подхватывает **сборка игры**, когда плагин едет вместе с ней, — файлы сборки
движка вы не правите никогда, просто кладёте папку плагина. Правила обнаружения:

* Папка добавляется, только если в ней есть **`CMakeLists.txt`**.
* Папки ищутся сначала в **корне проекта** (родитель `ICE_CONTENT_DIR`, когда собирается
  игровой проект), затем в **корне движка**; побеждает первая папка с данным именем, так
  что проект может перекрыть плагин движка.
* Если существует `Config/Plugins.json` с объектом `Enabled`, конфигурируются только
  перечисленные там плагины со значением `true` — остальные пропускаются с сообщением
  `Skipping disabled plugin '<name>' (not enabled in Plugins.json)`. **Отмечайте новый
  плагин в *Инструменты → Плагины и моды* до сборки игры с ним.**
* Плагин, чей `plugin.json` объявляет `"EditorOnly": true`, конфигурируется **только**
  для сборок редактора. Любая рантайм-конфигурация пропускает его с сообщением
  `Skipping editor-only plugin '<name>' (never built into a game)`.
* Сборки игр могут полностью отказаться от плагинов через `-DICE_INCLUDE_PLUGINS=OFF`
  (и от модов через `-DICE_INCLUDE_MODS=OFF`) — именно это выставляют опции сборки
  **Включить плагины** / **Включить моды** в редакторе (см.
  [раздел 7](#7-поставка-плагинов-и-модов-в-сборке)).

Минимальный `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.20)
project(MyPlugin LANGUAGES CXX)

if(ICE_PLUGIN_BUILD_STATIC)
    add_library(MyPlugin STATIC Source/MyPlugin.cpp)
    target_compile_definitions(MyPlugin PRIVATE ICE_PLUGIN_STATIC_BUILD)
else()
    add_library(MyPlugin SHARED Source/MyPlugin.cpp)
endif()

# Plugin SDK предоставляет PluginInterface.h и (для UI редактора) imgui::imgui.
target_link_libraries(MyPlugin PRIVATE IceBoxPluginSDK)

# Без префикса "lib"; движок ищет "<Name>.dll/.so/.dylib".
set_target_properties(MyPlugin PROPERTIES PREFIX "" OUTPUT_NAME "MyPlugin")

# Положить манифест рядом с динамической библиотекой, чтобы движок мог его прочитать.
if(NOT ICE_PLUGIN_BUILD_STATIC)
    add_custom_command(TARGET MyPlugin POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_if_different
            "${CMAKE_CURRENT_SOURCE_DIR}/plugin.json"
            "$<TARGET_FILE_DIR:MyPlugin>/plugin.json")
endif()
```

Примечания:

* **`IceBoxPluginSDK`** — это INTERFACE-таргет. Он добавляет `Source/Engine/Core` в пути
  включения (там лежит `PluginInterface.h`), линкует `nlohmann_json` и `fmt`, добавляет
  `imgui::imgui`, когда ImGui доступен, и требует **C++23**. Линкуйте его как `PRIVATE`.
* Защищайте редакторские плагины (те, что включают `imgui.h`), чтобы они **пропускались**
  на платформах, где неприменимы — например `if(ANDROID OR EMSCRIPTEN OR IOS) return()
  endif()` и `if(NOT TARGET imgui::imgui) return() endif()`, как делает встроенный
  AIHelper. Его файл сборки лежит рядом с плагином как
  `Plugins/AIHelper/CMakeLists.txt.example` — целиком рабочий образец, который можно
  скопировать. Суффикс `.example` нужен для того, чтобы ни сборка игры, ни Plugin Builder
  не приняли встроенный бинарный плагин за плагин, который надо компилировать.
* Движок задаёт `ICE_PLUGIN_OUTPUT_DIR` туда, где библиотека должна оказаться, чтобы
  именно эта сборка её нашла: `Plugins/<Name>/` рядом с редактором в сборке
  **редактора**, `bin/<platform>/Plugins/<Name>/` рядом с исполняемым файлом игры в
  сборке **рантайма/игры**, `lib/Android/<ABI>/` на Android и `static_plugins/<Name>/`
  для статических сборок. Учитывайте его, если кастомизируете пути вывода (в
  `Plugins/AIHelper/CMakeLists.txt.example` показан полный набор свойств
  `RUNTIME_/LIBRARY_/PDB_OUTPUT_DIRECTORY*` для мультиконфигурационных генераторов).
  Из этой же папки сборка игры берёт плагин в дистрибутив — плагин, игнорирующий
  `ICE_PLUGIN_OUTPUT_DIR`, в поставку не попадёт.
* Добавьте `add_dependencies(IceBoxRuntime <plugin>)` под `if(TARGET IceBoxRuntime)`,
  чтобы плагин пересобирался в каждой сборке игры, которая его включает. В
  `Plugins/AIHelper/CMakeLists.txt.example` точно так же закрыт
  `add_dependencies(IceBoxEngine <plugin>)`: такая цель существует только в дереве
  исходников движка, поэтому везде ещё условие просто не срабатывает. Наличие обоих
  делает один `CMakeLists.txt` пригодным и там, и там.

### 3.11 Рабочий пример: минимальный плагин редактора

`Plugins/MyPlugin/Source/MyPlugin.cpp`:

```cpp
#include "PluginInterface.h"
#include <imgui.h>

namespace {

class MyPlugin final : public IceBox::IPlugin {
public:
    IceBox::PluginInfo GetPluginInfo() const override {
        IceBox::PluginInfo info;
        info.Name        = "MyPlugin";
        info.Description  = "Adds a Hello panel to the editor.";
        info.Author      = "You";
        info.Version     = "1.0.0";
        info.APIVersion  = IceBox::ICE_PLUGIN_API_VERSION;
        return info;
    }

    bool OnLoad() override  { return true; }
    void OnUnload() override {}

    void OnEditorInit(const IceBox::EditorPluginContext& ctx) override {
        m_Ctx = ctx;
        if (ctx.ImGuiCtx) ImGui::SetCurrentContext(ctx.ImGuiCtx);
        if (ctx.ImGuiAllocFn && ctx.ImGuiFreeFn)
            ImGui::SetAllocatorFunctions(ctx.ImGuiAllocFn, ctx.ImGuiFreeFn, ctx.ImGuiUserData);
    }

    void OnEditorToolsMenu() override {
        if (ImGui::MenuItem("My Plugin", nullptr, m_Show)) m_Show = !m_Show;
    }

    void OnEditorUI(float /*dt*/) override {
        if (!m_Show) return;
        if (ImGui::Begin("My Plugin", &m_Show)) {
            ImGui::TextUnformatted("Hello from a native plugin!");
            if (ImGui::Button("Spawn an entity") && m_Ctx.Host)
                m_Ctx.Host->CreateEntity(m_Ctx.HostContext, "FromPlugin");
        }
        ImGui::End();
    }

private:
    IceBox::EditorPluginContext m_Ctx{};
    bool m_Show = false;
};

}

ICE_PLUGIN_ENTRY(MyPlugin)
```

Положите это (плюс `plugin.json` и `CMakeLists.txt` выше) в `Plugins/MyPlugin/`,
соберите его через [Plugin Builder](#313-сборка-плагина--plugin-builder), отметьте
в *Инструменты → Плагины и моды* — и найдёте *Инструменты → My Plugin*.

### 3.12 Поставка данных и нод Visual Script вместе с плагином

Папка плагина — это больше, чем библиотека: движок относится к ней ещё и как к небольшому
пакету.

**Папки данных.** `Content/`, `Assets/`, `Scripts/` и `Lua/` внутри папки плагина
упаковываются вместе с плагином на Web (встраиваются в `.data` Emscripten) и iOS
(копируются в подписанный `.app`); на Web дополнительно встраиваются и отдельные `*.lua`
в корне плагина. Загружайте их в рантайме относительно `PluginFolderPath`.

**Ноды Visual Script.** Если в папке плагина есть `VisualScriptAPI.json`, редактор
загружает его вместе с собственным `Config/VisualScriptAPI.json` движка и превращает
записи в ноды редактора Visual Script. Именно так плагин, регистрирующий Lua-функции
(через `OnRegisterLua`), делает их доступными без написания кода. Формат файла тот же,
что и у каталога движка:

```json
{
    "version": 1,
    "functions": [
        {
            "name": "MyPluginPing",
            "call": "MyPluginPing",
            "surface": "class",
            "category": "MyPlugin",
            "pure": false,
            "args": [
                { "name": "message", "type": "String", "opt": false }
            ],
            "ret": "Bool"
        }
    ]
}
```

| Ключ | Значение |
| ---- | -------- |
| `name` | Имя функции, а также заголовок ноды, если не заданы `title`/`call`. |
| `call` | Выражение Lua, которое реально генерируется. |
| `title` | Явный заголовок ноды (по умолчанию `call`, если в нём есть точка, иначе `name`). |
| `surface` | Где предлагается нода: `class`, `level`, `widget`, `any`. |
| `category` | Категория палитры. |
| `pure` | `true` для value-ноды без пинов исполнения. |
| `ret` / `rets` | Один тип возврата либо список именованных выходов. |
| `args` | Входные пины: `name`, `type`, опционально `picker`, `values` (enum), `default`, `opt`. |
| `method`, `object`, `colon` | Генерировать `object.name(...)` / `object:name(...)` вместо свободной функции. |

Дубликаты имён игнорируются, а записи, конфликтующие с курируемой нодой движка,
пропускаются — так что случайно перезаписать встроенную палитру нельзя.

### 3.13 Сборка плагина — Plugin Builder

Плагин никогда не линкуется с движком — он лишь подключает `PluginInterface.h` и
общается через таблицы функций хоста, — поэтому собирается полностью отдельно, без
всякой сборки движка. Так собирается любой ваш плагин.

Ровно это и делает `Tools/PluginBuilder/`, который поставляется с каждой установкой
движка:

| Платформа | Скрипт |
| --------- | ------ |
| Windows | `Tools\PluginBuilder\build_plugins_windows.bat` |
| Linux | `Tools/PluginBuilder/build_plugins_linux.sh` |
| macOS | `Tools/PluginBuilder/build_plugins_macos.sh` |

Запустите один из них — он просканирует `Plugins/`, покажет все плагины с их
состоянием (`NOT BUILT` — не собран, `OUTDATED` — исходники новее библиотеки, `BUILT` —
актуален, `NO BUILD` — нет `CMakeLists.txt`, собирать нечего) и предложит выбрать, что
собирать. По Enter собирается всё, что этого требует.

Для каждого выбранного плагина конфигурируется маленький CMake-проект
`Tools/PluginBuilder/Harness/`, который воссоздаёт INTERFACE-цель `IceBoxPluginSDK`
поверх заголовков движка из `Source/Engine/Core`, подключает плагин через
`add_subdirectory()` и собирает **только плагин** во временное дерево в
`out/pluginbuild/`. Готовая библиотека копируется в папку плагина, и та принимает вид:

```
Plugins/AIHelper/
    plugin.json
    AIHelper.dll        (.so на Linux, .dylib на macOS)
```

Эта папка и есть готовый к передаче плагин: запакуйте её, отдайте человеку — он кладёт
её в свою `Plugins/` и включает галочкой в *Инструменты → Плагины и моды*. Внутри папки
плагина ничего не компилируется, поэтому объектных файлов и кэшей CMake там не остаётся.

Зависимости (`nlohmann-json`, `fmt` и docking-сборка `imgui`) разрешаются в таком
порядке: явный `--vcpkg-installed <dir>`, затем любое дерево
`vcpkg_installed/<triplet>`, которое уже оставила на этой машине сборка движка или
игры, затем vcpkg по манифесту `Harness/vcpkg.json` — в нём закреплены baseline движка,
его набор фич ImGui и его overlay-порты. Харнесс отказывается собирать плагин против
ImGui без docking, потому что такой плагин испортит состояние интерфейса редактора на
первом же кадре.

Со сборкой движка, в которую вы грузите плагин, должны совпасть три вещи:
**конфигурация** (`Release` ↔ `Release`), **архитектура** и **версия ABI**
([3.9](#39-версионирование-api--abi)). Полный список параметров, примеры и разбор
типичных ошибок — в `Tools/PluginBuilder/README.ru.md` (на английском: `README.md`).

# Часть II — Моды (Lua + контент)

## 4. Система модов

Мод — это папка в `Mods/`, содержащая манифест `mod.json`, входной Lua-скрипт и любой
поставляемый контент. Движок находит её и при включении запускает входной скрипт в
**песочничной среде Lua**, затем отправляет ему хуки жизненного цикла. Моды никогда не
компилируются и могут переключаться «на лету».

> **Моды — рантаймовая возможность.** Они загружаются при старте Play-режима (или
> собранной игры) и выгружаются при его остановке — во время обычного редактирования они
> не работают. Об этом же напоминает подпись внизу списка на вкладке Mods.

### 4.1 Что может мод

* **Поставлять контент** — упаковывать игровые объекты `.ice_class`, интерфейсы `.ice_widget`,
  спрайты, текстуры и любые другие ассеты внутри папки мода, ссылаясь на них относительно
  каталога мода.
* **Спавнить и управлять геймплеем** — инстанцировать свои классы во время выполнения,
  планировать таймеры, читать/записывать общее игровое состояние и в целом использовать
  **Lua API** движка.
* **Встраиваться в жизненный цикл уровня** — выполнять логику при загрузке/выгрузке мода,
  при старте/конце уровней, каждый кадр и на фиксированном тике.
* **Разбиваться на модули** — подгружать дополнительные Lua-файлы из своей папки через
  `ModRequire`.
* **Неразрушающе расширять пример/базовую игру** — добавлять механики и UI без правки
  файлов базовой игры.

> То, что мод *может вызывать*, — это Lua API движка (например, `SpawnEntity`,
> `SetInterval`, `GetGameInt`/`SetGameInt`, …). Этот API описан в
> [LuaAPI-RU-DOC.md](LuaAPI-RU-DOC.md), где раздел **§41 Моды** является
> скриптовым дополнением к этой главе. Данный документ охватывает *структуру* и
> *жизненный цикл* мода.

### 4.2 Анатомия мода

```
Mods/MyMod/
    mod.json                      # манифест (имя, версия, входной скрипт, порядок загрузки …)
    main.lua                      # входной скрипт (выполняется в песочничной среде)
    Icon.png                      # опциональная иконка во вкладке Mods
    README.md                     # опционально; индексируется плагином AI Helper
    modules/                      # опциональный доп. Lua, подгружаемый через ModRequire
        helpers.lua
    Content/                      # ассеты, поставляемые модом
        Classes/   *.ice_class
        Widgets/   *.ice_widget
        Assets/    *.png, *.ice_sprite, ...
```

Это повторяет встроенный `Mods/PlatformerCrates`, поставляющий класс ящика, класс HUD,
виджет HUD и спрайт/текстуру.

### 4.3 Манифест `mod.json`

```json
{
    "Name": "MyMod",
    "Description": "Spawns a pickup when a level starts.",
    "Author": "You",
    "Version": "1.0.0",
    "Icon": "Icon.png",
    "EntryScript": "main.lua",
    "LoadOrder": 100,
    "APIVersion": 1,
    "Dependencies": []
}
```

| Поле | Значение | По умолчанию |
| ---- | -------- | ------------ |
| `Name` | Уникальное имя мода (совпадает с `Mods.json`). | имя папки |
| `Description` | Показывается во вкладке Mods. | `""` |
| `Author` | Показывается во вкладке Mods. | `""` |
| `Version` | Отображаемая версия; также доступна скрипту как `MOD_VERSION`. | `"1.0.0"` |
| `Icon` | Путь (относительно папки мода) к иконке `.png` / `.jpg` / `.jpeg`. | автоопределение |
| `EntryScript` | Lua-файл, запускаемый при загрузке. | `main.lua` |
| `LoadOrder` | Меньшие значения загружаются раньше. | `100` |
| `APIVersion` | Версия API модов, на которую рассчитан мод. | `1` |
| `Dependencies` | Имена других модов, которые должны загрузиться первыми. | `[]` |

Разрешение иконки такое же, как у плагинов — см. [3.3](#33-манифест-pluginjson).

> **`APIVersion` сверяется с версией ABI плагинов движка** (сейчас **4**). Мод,
> объявивший большее число, отвергается с сообщением
> `Mod '<name>' requires API version N (engine has 4)`. Оставляйте `1`, если нет причин
> поднимать значение.

### 4.4 Среда мода и внедряемые глобалы

Входной скрипт каждого мода выполняется в **собственной песочничной среде Lua**, так что
локали/глобалы верхнего уровня мода не конфликтуют с другими модами или скриптом уровня.
Среда наследует глобальный Lua API движка, а когда сцена активна, в неё дополнительно
привязывается API уровня. Движок внедряет следующие глобалы:

| Глобал | Значение |
| ------ | -------- |
| `MOD_NAME` | Имя мода. |
| `MOD_VERSION` | Строка версии мода. |
| `MOD_DIR` | Абсолютный путь к папке мода (прямые слеши). Используйте для ссылок на поставляемый контент. |
| `ModRequire(name)` | Подгружает другой Lua-файл этого мода. См. ниже. |

Ссылайтесь на поставляемый контент относительно `MOD_DIR`:

```lua
local PICKUP = MOD_DIR .. "/Content/Classes/CL_Pickup.ice_class"
```

**`ModRequire`** — это мод-локальный аналог `require`. Он заменяет `.` на `/`, добавляет
`.lua`, разрешает путь относительно `MOD_DIR`, выполняет файл **в той же песочнице**, что
и мод (так что `MOD_NAME`/`MOD_DIR` там тоже видны), и возвращает то, что вернул файл:

```lua
local helpers = ModRequire("modules.helpers")   -- <MOD_DIR>/modules/helpers.lua
if helpers then helpers.SayHello() end
```

Он «мягко» падает: отсутствующий файл, синтаксическая ошибка или ошибка выполнения
логируются с именем мода, `ModRequire` возвращает `nil`, а остальной мод продолжает
загружаться. Кэша результатов нет — каждый вызов выполняет файл заново.

### 4.5 Хуки жизненного цикла

Определяйте их как **глобальные функции** во входном скрипте (или в файле, подключённом
через `ModRequire`). Движок вызывает их автоматически:

| Хук | Когда |
| --- | ----- |
| `OnModLoad()` | Один раз, сразу после загрузки скрипта мода — до выполнения скрипта уровня при старте play. (Если мод включён по ходу сессии, когда уровень уже активен, далее вызывается и `OnLevelStart()`.) |
| `OnLevelStart()` | Каждый раз, когда уровень становится активным, **после** инициализации скрипта уровня и всех скриптов сущностей. Отправляется каждому загруженному моду. |
| `OnLevelUpdate(dt)` | Каждый кадр, пока идёт уровень — после `OnLevelUpdate` скрипта уровня и до скриптов сущностей. |
| `OnLevelFixedUpdate(dt)` | Каждый фиксированный тик — используйте для всего, что связано с физикой. |
| `OnLevelLateUpdate(dt)` | Каждый кадр, после основного прохода обновления. |
| `OnLevelEnd()` | Каждый раз, когда активный уровень завершается/выгружается. Отправляется каждому загруженному моду. |
| `OnModUnload()` | Когда мод выгружается (отключён или при завершении работы). Очищайте здесь таймеры, заспавненные сущности и т. п. |

Типичный паттерн: настраивайте состояние и таймеры в `OnLevelStart`, сворачивайте их в
`OnLevelEnd`/`OnModUnload`.

Ошибки локальны для мода и не фатальны: упавший хук логируется как
`[Mod:<name>] <hook> error: …`, а остальные моды всё равно получают то же событие.
Покадровые хуки не вызываются, пока выполнение приостановлено Lua-отладчиком.

### 4.6 Поставка контента с модом

Ассеты, помещённые внутрь папки мода, путешествуют вместе с модом. Ссылайтесь на них по
пути, построенному от `MOD_DIR`. Поставляемые игровые объекты `.ice_class` могут нести **свои
собственные** встроенные скрипты и компоненты — например, встроенный класс ящика
использует скрипт `OnSensorEnter`, чтобы обнаружить игрока, увеличить общий счётчик и
уничтожить себя, а виджет HUD читает этот счётчик каждый кадр. Это значит, что мод может
поставлять цельные, самодостаточные механики чисто как контент + тонкий входной скрипт.

Браузер контента индексирует дерево `Content/` проекта, а не `Mods/`, поэтому ассеты мода
не видны в редакторе — и это by design: мод сам разрешает свои файлы через `MOD_DIR` во
время выполнения. О типах ассетов, которые можно поставлять (спрайты, классы, виджеты,
материалы, …) и как они работают, см. [Ассеты и Браузер контента](Assets-RU-DOC.md).

### 4.7 Порядок загрузки и зависимости

* Моды загружаются по возрастанию **`LoadOrder`** (по умолчанию `100`). Используйте
  меньшее число, чтобы загрузиться раньше, большее — чтобы позже.
* **`Dependencies`** перечисляет имена других модов, которые должны загрузиться первыми.
  Движок разрешает порядок сортировкой с учётом зависимостей поверх последовательности
  `LoadOrder` и **обнаруживает циклы** (мод в цикле зависимостей или тот, чья зависимость
  отсутствует, сломана либо не включена, пропускается с предупреждением).
* **У плагинов всё устроено так же.** `Dependencies` из `plugin.json` разрешаются той же
  сортировкой с обнаружением циклов ещё до загрузки, и плагин со сломанной или
  отсутствующей зависимостью пропускается с предупреждением.

### 4.8 Рабочий пример: минимальный мод

`Mods/MyMod/mod.json` — см. [4.3](#43-манифест-modjson).

`Mods/MyMod/main.lua`:

```lua
local PICKUP = MOD_DIR .. "/Content/Classes/CL_Pickup.ice_class"
local timerId = 0

function OnModLoad()
    print(string.format("[%s] v%s loaded from %s", MOD_NAME, MOD_VERSION, MOD_DIR))
end

function OnLevelStart()
    -- Заспавнить один пикап сразу, затем по одному каждые 5 секунд.
    SpawnEntity(PICKUP, 0.0, 0.0, 0.0)
    timerId = SetInterval(5.0, function()
        SpawnEntity(PICKUP, 0.0, 0.0, 0.0)
    end)
end

function OnLevelEnd()
    if timerId ~= 0 then CancelTimer(timerId); timerId = 0 end
end

function OnModUnload()
    if timerId ~= 0 then CancelTimer(timerId); timerId = 0 end
end
```

Положите папку в `Mods/`, поставьте `CL_Pickup.ice_class` в
`Mods/MyMod/Content/Classes/`, включите **MyMod** во вкладке Mods — и он отработает при
следующем нажатии Play, без пересборки. (`SpawnEntity`, `SetInterval`, `CancelTimer` —
Lua-функции движка; см. доку Lua API.)

# Часть III — Управление и поставка

## 5. Управление плагинами и модами

### 5.1 Панель Plugins & Mods

Откройте её из `Инструменты → Плагины и моды`. У неё до трёх вкладок:

* **Plugins (C++)** — каждый найденный плагин с иконкой, **флажком включения**, именем
  (зелёное, когда **загружен**, иначе серое), версией, значком `[Loaded]`, значком
  `[Editor Only]` у плагинов с `"EditorOnly": true`, описанием, автором и кнопкой
  **Show in File Browser**.
* **Mods (Lua)** — та же раскладка для модов, плюс **Load Order** каждого мода. Мод,
  который включён, но ещё не запущен, показывает жёлтый значок `[Pending]`; работающий
  становится зелёным со значком `[Loaded]`.
* **Settings** — появляется, только если загруженный плагин зарегистрировал страницу
  настроек (через `RegisterSettingsPage`); показывает эти страницы по категориям.

У обеих вкладок со списками есть кнопка **Refresh** и **поле поиска**, фильтрующее список
по имени (подстрока, без учёта регистра). Переключение флажка немедленно записывает
соответствующий файл конфигурации. Видимость самой панели запоминается в
`Config/Editor.json` в `PanelVisibility.PluginsPanel`.

**Что на самом деле делают кнопки:**

| Действие | Эффект |
| -------- | ------ |
| Флажок плагина включён | Загружает плагин **сразу**, если его библиотека на месте, диспатчит `OnEngineInit`, затем `OnEditorInit`, и сохраняет `Config/Plugins.json`. Его пункты Tools, панели и типы ассетов появляются немедленно. |
| Флажок плагина выключен | Выгружает плагин, снимает всё, что он зарегистрировал, и сохраняет конфиг. |
| **Refresh** для плагинов | Выгружает все плагины, пере-сканирует `Plugins/`, перечитывает конфиг, загружает включённые и заново вызывает `OnEditorInit`. Используйте после пересборки плагина. |
| Флажок мода | Сохраняет `Config/Mods.json`. Если уровень сейчас запущен, мод загружается/выгружается немедленно; иначе изменение вступит в силу при следующем Play. |
| **Refresh** для модов | Выгружает все моды и пере-сканирует `Mods/` + конфиг. |

> **Совершенно новому плагину всё равно нужна сборка.** Флажок лишь загружает уже
> существующую библиотеку, поэтому порядок такой: положить папку → собрать её через
> **Plugin Builder** ([3.13](#313-сборка-плагина--plugin-builder)) → отметить здесь →
> **Refresh**. Как только библиотека существует, включение и выключение работают «на
> лету».

### 5.2 Файлы конфигурации

Два небольших файла в `Config/` фиксируют, какие расширения включены:

`Config/Plugins.json`:

```json
{
    "SearchDirectory": "Plugins",
    "Enabled": {
        "AIHelper": true
    }
}
```

`Config/Mods.json`:

```json
{
    "SearchDirectory": "Mods",
    "Enabled": {
        "PlatformerCrates": false
    }
}
```

| Поле | Значение |
| ---- | -------- |
| `SearchDirectory` | Папка, сканируемая на плагины/моды (`Plugins` / `Mods`). Смена значения перезапускает дискавери по этой папке. |
| `Enabled` | Карта `имя → bool`. Загружаются, конфигурируются в CMake и упаковываются в сборки только записи со значением `true`. |

Эти файлы можно править вручную; редактор перезаписывает их при переключении флажков,
подмешивая изменения в остальное содержимое файла.

> **Инсталляции только для чтения.** Если конфиг лежит внутри macOS-бандла `.app`, движок
> считает поставляемый файл базой, а пользовательские переопределения пишет и читает из
> записываемого каталога конфигурации — так выбор игрока сохраняется, не трогая
> подписанный бандл.

### 5.3 Управление модами из Lua

Моды также можно инспектировать и настраивать во время выполнения из скрипта через модуль
`Mods` движка — это основа для внутриигрового меню модов:

| Функция | Возвращает |
| ------- | ---------- |
| `Mods.GetAll()` | Массив таблиц: `name`, `description`, `author`, `version`, `enabled`, `loaded`, `loadOrder`. |
| `Mods.GetInfo(name)` | Ту же таблицу плюс `entryScript` и `folderPath`, либо `nil`. |
| `Mods.GetCount()` / `Mods.GetEnabledCount()` | Итоговые количества. |
| `Mods.IsEnabled(name)` / `Mods.IsLoaded(name)` | Булевы значения. |
| `Mods.SetEnabled(name, enabled)` | Включает/выключает и **сохраняет** `Config/Mods.json`. |
| `Mods.Refresh()` | Выгружает все моды, пере-сканирует `Mods/`, перечитывает конфиг и загружает включённые. |

```lua
Mods.SetEnabled("PlatformerCrates", false)
Mods.Refresh()
```

Весь модуль также доступен как ноды **Visual Script** в категории `Mods`. Полный
справочник см. в [LuaAPI-RU-DOC.md](LuaAPI-RU-DOC.md).

### 5.4 Вкладка Plugins & Mods в лаунчере

Лаунчер управляет пакетами **на уровне проекта** — на ступень выше, чем «движковый» вид
редактора. Его вкладка **Plugins & Mods** (также доступная из контекстного меню проекта
через *Manage Plugins & Mods…*, что сразу выбирает этот проект) перечисляет всё, что
найдено в папках `Plugins/` и `Mods/` **движка** — имя, версию, автора, описание и
иконку прямо из манифестов — и позволяет отметить, что должен использовать проект.

Нажатие **Apply** записывает выбор в манифест проекта `.iceproject` как строковые
массивы `"Plugins"` и `"Mods"` (имена папок), а затем приводит папку проекта в
соответствие: копирует отмеченное и удаляет папки того, с чего отметку сняли. Полный
разбор этой вкладки, включая то, какой сборочный мусор отсеивается при копировании, —
в [Начало работы → Плагины и моды](Getting-Started-RU-DOC.md#34-плагины-и-моды).

Здесь важны два следствия:

* Подключённый так пакет живёт **внутри проекта**, поэтому проект несёт собственную его
  копию независимо от той установки движка, в которой был создан.
* Проектные папки `Plugins/` учитываются и при сборке: CMake ищет в корне проекта
  раньше, чем в корне движка, так что проект может поставлять — или перекрывать —
  плагин ([3.10](#310-файл-cmakeliststxt-плагина)).

### 5.5 Плагины и моды, установленные игроком

Собранные игры на **macOS и iOS** дополнительно ищут пользовательские пакеты за
пределами бандла приложения. При первом запуске рантайм создаёт пользовательский корень
контента — записываемый каталог данных приложения либо `~/Documents` на iOS — с папками
`Saves/`, `Config/`, `Mods/`, `Plugins/` и коротким `README.txt` с описанием раскладки.

Любая папка, положенная в такие `Mods/` или `Plugins/` и содержащая корректный
`mod.json` / `plugin.json`, обнаруживается после собственных пакетов игры,
**включается автоматически** и пропускается с записью в лог, если пакет с таким именем
уже поставляется с игрой. Именно это позволяет игрокам ставить моды в подписанную сборку
только для чтения.

## 6. Как загружаются плагины и моды

**Менеджер плагинов** — единая подсистема движка, используемая и редактором, и рантаймом.
Её поток:

1. **Дискавери** — просканировать `Plugins/` и `Mods/` на подпапки с `plugin.json` /
   `mod.json` (для плагинов также включаются зарегистрированные статически; моды
   сортируются по `LoadOrder`). В редакторе отсутствующие папки создаются.
2. **Чтение конфига** — загрузить `Config/Plugins.json` и `Config/Mods.json`, чтобы знать,
   что включено. Если в конфиге указан другой `SearchDirectory`, дискавери
   перезапускается по нему.
3. **Загрузка включённых плагинов** — разрешить порядок зависимостей (пропуская циклы и
   сломанные зависимости), затем для каждого плагина: загрузить библиотеку (или
   использовать статическую регистрацию), разрешить `CreatePlugin`, создать экземпляр,
   проверить **версию API**, вызвать `OnLoad`, «доиграть» `OnRegisterLua` для уже
   существующих Lua-состояний, затем `OnEngineInit`, а в редакторе — `OnEditorInit`.
   Вне редактора плагины с `"EditorOnly": true` пропускаются до всего этого (и не
   учитываются при разрешении зависимостей других плагинов).
4. **Загрузка включённых модов** — это происходит при **старте play/рантайма**, а не при
   запуске редактора. Разрешить порядок из `LoadOrder` + зависимостей (пропуская циклы),
   запустить входной скрипт каждого мода в его песочничной среде и вызвать `OnModLoad`.
5. **Диспатч** — переправлять `OnUpdate` (кадры рантайма), старт/стоп рантайма,
   старт/конец/обновление уровня, регистрацию Lua/Python и события загруженным
   плагинам/модам с учётом версии API, где это уместно. Каждый диспатч защищён от
   исключений.

Шаги 1–3 выполняются один раз при старте редактора или игры; шаг 4 — при каждом Play.

**Выгрузка.** Моды выгружаются при остановке play в **обратном** порядке загрузки,
получая `OnLevelEnd`, затем `OnModUnload`. Плагины выгружаются при завершении работы
(или когда вы снимаете флажок) в порядке обнаружения; у каждого сначала снимаются все
сделанные им регистрации в редакторе, затем вызываются `OnUnregisterLua`,
`OnEditorShutdown` (если его редакторская часть ещё жива) и `OnUnload`, и только потом
освобождается библиотека.

## 7. Поставка плагинов и модов в сборке

### 7.1 Два переключателя сборки

В диалоге **Build Game** есть секция **Packages** с двумя флажками. Оба **включены** по
умолчанию и запоминаются в `Config/Editor.json` (`BuildSettings.IncludePlugins` /
`BuildSettings.IncludeMods`):

| Опция | Эффект |
| ----- | ------ |
| **Включить плагины** | Включено: плагины, отмеченные в панели Plugins & Mods, компилируются (или линкуются статически) и упаковываются под целевую платформу. Выключено: ни один плагин не конфигурируется, не собирается, не линкуется, не копируется и не встраивается, а `Config/Plugins.json` не поставляется. |
| **Включить моды** | Включено: моды, отмеченные в панели, упаковываются под целевую платформу. Выключено: ни одна папка мода не копируется и не встраивается, а `Config/Mods.json` не поставляется. |

Под каждым флажком диалог показывает, сколько включённых пакетов реально уедет в сборку,
и сколько включённых плагинов пропускается как **чисто редакторские**.

Обе опции действуют на **все шесть платформ**. Они передаются сборочным скриптам как
`--no-plugins` / `--no-mods`, которые пробрасывают в CMake `-DICE_INCLUDE_PLUGINS=OFF` /
`-DICE_INCLUDE_MODS=OFF`, поэтому статическая линковка Web/iOS, нативные библиотеки и
ассеты APK на Android и шаг копирования на десктопе принимают одно и то же решение.

Выключение опции — это решение только про **поставку**: оно не трогает
`Config/Plugins.json` / `Config/Mods.json` в вашем проекте и не влияет на то, что
работает в редакторе.

### 7.2 Что делает сборка

Когда вы собираете игру (см.
[Профайлинг и сборка игр](Profiling-And-Building-RU-DOC.md)), сборка:

* Копирует в вывод **только включённые** плагины и моды (согласно `Plugins.json` /
  `Mods.json`, которые читаются сначала из проекта, затем из движка), логируя каждый
  пропущенный пакет, и копирует рядом два файла конфигурации.
* **Никогда** не копирует, не накладывает, не линкует и не встраивает плагин, чей
  `plugin.json` объявляет `"EditorOnly": true` — ни на одной платформе, что бы ни было
  написано в `Plugins.json`.
* Отфильтровывает сборочный мусор при копировании — папки `Source/`, `src/`, `build/`,
  `out/`, `CMakeFiles/`, `.cache/`, `.vs/`, `.vscode/`, `.idea/`, `.git/`,
  `node_modules/` и `__pycache__/`, файлы `.obj/.o/.lib/.a/.exp/.ilk/.pdb/.pyc/.pyo/.cmake`,
  а также `CMakeLists.txt` / `CMakeCache.txt` / `.gitignore` / `.gitattributes`.
* Затем **накладывает сверху собранные артефакты плагинов**: только скомпилированную
  библиотеку (`.dll`/`.so`/`.dylib`), её `.pdb` (если есть) и `plugin.json`.
* Для **модов** поставляет всю папку включённого мода (его `Content/`, `main.lua`,
  `mod.json`, иконку, README), поскольку моды загружаются как есть во время выполнения.

Размещение по платформам:

| Платформа | Плагины | Моды |
| --------- | ------- | ---- |
| Windows / Linux | `<Вывод>/Plugins/<Name>/` | `<Вывод>/Mods/<Name>/` |
| macOS | `<Игра>.app/Contents/Resources/Plugins/` | `<Игра>.app/Contents/Resources/Mods/` |
| Android | `.so` → `jniLibs/<ABI>/` внутри APK, остальная папка → `assets/Plugins/<Name>/` | стейджатся в `assets/Mods` внутри APK |
| iOS | линкуются статически; `plugin.json` + папки данных кладутся в подписанный `.app` | кладутся в бандл `.app` |
| Web | линкуются статически в рантайм | встраиваются в `.data` Emscripten через `--preload-file` |

Cooked-сборки дополнительно кладут `Config/`, `Plugins/` и `Mods/` рядом с приготовленным
контентом, чтобы упакованная игра видела ту же раскладку — и пропускают стейджинг
`Plugins/` или `Mods/`, когда соответствующая опция **Include** выключена.

В результате поставляемая игра загружает ровно те плагины и моды, которые вы включили,
через тот же поток менеджера плагинов, что и редактор.

## 8. Сводный справочник

### 8.1 Плагины vs Моды

| | Плагины | Моды |
| --- | ------- | ---- |
| Форма | Нативная C++-библиотека / статика | Папка Lua + контент |
| Манифест | `plugin.json` | `mod.json` |
| Вход | `ICE_PLUGIN_ENTRY(Class)` → `IPlugin` | `main.lua` |
| SDK / API | `IceBoxPluginSDK`, C-ABI v`4` | Lua API движка, `APIVersion` мода (≤ `4`) |
| Папка / конфиг | `Plugins/` · `Config/Plugins.json` | `Mods/` · `Config/Mods.json` |
| Живут в | Редакторе + рантайме | Только Play-режиме / игре |
| Переключение «на лету» | Да, если собран | Да |
| Попадает в сборку, когда | включена **Включить плагины**, пакет включён и он не `EditorOnly` | включена **Включить моды** и пакет включён |

### 8.2 Хуки IPlugin

`GetPluginInfo` · `OnLoad` · `OnUnload` · `OnUpdate` · `OnRuntimeStart` ·
`OnRuntimeStop` · `OnEngineInit` · `OnEditorInit` · `OnEditorShutdown` ·
`OnEditorToolsMenu` · `OnEditorUI` · `OnRegisterLua` · `OnUnregisterLua` ·
`OnRegisterPython` · `OnEditorEvent` · `OnEngineEvent`

Регистрация в редакторе: `RegisterPanel` · `RegisterAssetType` · `RegisterMenuItem` ·
`RegisterToolbarButton` · `RegisterViewportOverlay` · `RegisterContextMenuItem` ·
`RegisterSettingsPage` (+ `ShowPanel` · `IsPanelOpen`)

### 8.3 Хуки и глобалы мода

Хуки: `OnModLoad` · `OnLevelStart` · `OnLevelUpdate` · `OnLevelFixedUpdate` ·
`OnLevelLateUpdate` · `OnLevelEnd` · `OnModUnload`
Глобалы: `MOD_NAME` · `MOD_VERSION` · `MOD_DIR` · `ModRequire`
Модуль Lua: `Mods.GetAll` · `GetInfo` · `GetCount` · `GetEnabledCount` · `IsEnabled` ·
`IsLoaded` · `SetEnabled` · `Refresh`

### 8.4 Файлы и папки

| Путь | Что это |
| ---- | ------- |
| `Plugins/<Name>/plugin.json` | Манифест плагина (папка с исходниками); `"EditorOnly": true` не пускает его ни в одну сборку игры. |
| `Plugins/<Name>/VisualScriptAPI.json` | Опциональные дополнительные ноды Visual Script. |
| `Mods/<Name>/mod.json` | Манифест мода. |
| `Config/Plugins.json` · `Config/Mods.json` | Какие пакеты включены. |
| `Config/Editor.json` → `PanelVisibility.PluginsPanel` | Открыта ли панель. |
| `Config/Editor.json` → `BuildSettings.IncludePlugins` / `.IncludeMods` | Переключатели **Packages** в Build Game. |
| `bin/<platform>/Plugins/<Name>/` | Собранная библиотека плагина + `plugin.json`. |
| `<Проект>.iceproject` → `"Plugins"`, `"Mods"` | Выбор пакетов на уровне проекта (лаунчер). |
| `<пользовательские данные>/Mods/`, `.../Plugins/` | Пакеты, подкладываемые игроком (сборки macOS/iOS). |

## 9. FAQ и устранение проблем

**Что писать — плагин или мод?**
Плагин для **инструментов редактора / нативной интеграции**; мод для **контента и
геймплея** через Lua. См. [Раздел 2](#2-плагины-vs-моды--что-выбрать).

**Я включил плагин, но ничего не произошло.**
Если его библиотека уже была собрана, включение загружает плагин немедленно. Если это
новый плагин, его ещё ничто не скомпилировало — соберите его через Plugin Builder
([3.13](#313-сборка-плагина--plugin-builder)) и нажмите **Refresh**. Также проверьте лог:
плагин, чей `APIVersion` новее, чем у движка, будет отвергнут, как и тот, в папке
которого нет `.dll`/`.so`/`.dylib`.

**Окна ImGui моего плагина не отображаются.**
Нужно перенять контекст и аллокатор ImGui хоста в `OnEditorInit` (Раздел
[3.7](#37-контексты-плагина-и-imgui)). Без этого вызовы ImGui из плагина уходят «в
никуда».

**`OnUpdate` моего плагина никогда не вызывается.**
`OnUpdate` — это **рантаймовый** тик: он срабатывает, только пока идёт игра или
Play-режим. Для покадровой работы в редакторе используйте `OnEditorUI`.

**Где движок ищет плагины/моды?**
В `Plugins/` и `Mods/` относительно рабочего каталога (настраивается через
`SearchDirectory` в файлах конфигурации). Скомпилированные плагины загружаются из
выходного каталога рантайма `Plugins/<Name>/`. На этапе конфигурации сборки CMake ищет
ещё и в корне проекта, а собранные игры для macOS/iOS дополнительно сканируют
записываемые пользовательские папки `Mods/`/`Plugins/`.

**Могут ли моды выполнять нативный код?**
Нет — моды это Lua + контент, в песочнице. Для нативного кода пишите плагин.

**Контент моего мода не находится.**
Стройте пути от `MOD_DIR` (например, `MOD_DIR .. "/Content/Classes/Foo.ice_class"`); не
прописывайте абсолютные пути жёстко. Дополнительные Lua-файлы подгружаются через
`ModRequire("папка.файл")`, тоже относительно `MOD_DIR`.

**Ассеты моего мода не появляются в Браузере контента.**
Так и задумано — браузер индексирует только дерево `Content/` проекта. Моды сами
разрешают свои файлы во время выполнения через `MOD_DIR`.

**Мод не загружается.**
Проверьте лог на: отсутствующую/сломанную/невключённую **зависимость**, **цикл**
зависимостей, `APIVersion` выше, чем поддерживает движок, или отсутствующий
`EntryScript`. Отключённые моды (в `Mods.json`) не загружаются — и ни один мод не
загрузится, пока вы не нажмёте **Play**.

**Поставляются ли плагины/моды с моей игрой?**
Только те, что **включены** в `Plugins.json` / `Mods.json`, и только пока в диалоге
Build Game включены опции **Включить плагины** / **Включить моды**. Плагины поставляются
как скомпилированные артефакты (исходники исключаются); моды поставляются всей папкой.
См. [Раздел 7](#7-поставка-плагинов-и-модов-в-сборке).

**Как не пустить редакторский инструмент в игру?**
Добавьте `"EditorOnly": true` в его `plugin.json`. После этого он показывает значок
`[Editor Only]` в панели Plugins, пропускается CMake во всех рантайм-конфигурациях,
никогда не копируется и не встраивается ни одной из шести платформенных сборок и
отклоняется менеджером плагинов вне редактора. В редакторе он продолжает работать как
обычно.

**Я выключил Include Plugins, а игра всё равно находит плагин.**
На macOS и iOS поставляемая игра дополнительно сканирует записываемую папку `Plugins/`
игрока ([5.5](#55-плагины-и-моды-установленные-игроком)); пакеты, которые игрок положил
туда сам, по-прежнему обнаруживаются. Опция сборки управляет только тем, что поставляет
*ваша* сборка.

**Как распространить плагин другим?**
Соберите его через Plugin Builder
([3.13](#313-сборка-плагина--plugin-builder)) и поделитесь **папкой** плагина:
после сборки в ней лежит `plugin.json` рядом с собранной библиотекой — это всё, что нужно
движку. Оставьте в ней `CMakeLists.txt` и `Source/`, если хотите, чтобы получатель мог
пересобрать плагин под свою платформу, конфигурацию или версию ABI движка.

**Как подключить плагин или мод к конкретному проекту?**
Используйте вкладку **Plugins & Mods** в лаунчере — она копирует пакет в проект и
записывает его в манифест `.iceproject`. См.
[Раздел 5.4](#54-вкладка-plugins--mods-в-лаунчере).
