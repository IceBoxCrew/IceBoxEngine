## 1. Введение

Между рабочим проектом и отполированной, готовой к поставке игрой стоят две вещи: знать,
*куда уходит время кадра*, и уметь *упаковать проект под каждую целевую платформу*.
IceBox предоставляет первоклассный инструментарий для обоих, встроенный и в редактор, и в
сам движок.

* **Профайлинг** работает в том же движке, который вы поставляете — профайлер
  живёт в ядре движка, а не в редакторе — так что измерения в редакторе отражают реальное
  поведение движка, а та же инструментация питает внешний профайлер **Tracy** в
  инструментированных сборках.
* **Сборка** управляется единым диалогом **Build Game**, который пишет конфигурацию для
  проекта и вызывает платформенные скрипты сборки в `Tools/BuildSystem/BuildGame/`. Тот же
  процесс выполняет подготовку, упаковку, манифесты и инсталляторы.

# Часть I — Профайлинг

## 2. Архитектура профайлинга

В сердце профайлинга — **профайлер движка**. Он работает и в
редакторе, и в рантайме, собирает покадровые метрики, управляет **скоупами** и
**трейсами** и является источником данных для панелей профайлинга редактора.

### 2.1 Что измеряет профайлер

Каждый кадр профайлер может собирать:

| Категория | Метрики |
| --------- | ------- |
| **Кадр** | Время кадра (мс), FPS, время кадра GPU (мс). |
| **CPU** | Загрузка CPU процессом (%, экспоненциально сглаженная), число физических ядер, число логических процессоров, частота (ГГц). |
| **Память** | RAM текущая / пиковая / всего (МБ), VRAM отслеживаемая / пиковая / всего (МБ, через трекер VRAM), число GPU-аллокаций. |
| **Температуры** | Температура CPU и GPU (°C), когда доступен источник, с именем источника (см. [2.4](#24-датчики-температуры)). |
| **Счётчики сцены** | Сущности, спрайты, вызовы отрисовки, квады, физические тела, активные скрипты, флипбуки, аудио, FX, источники света, прожекторы, камеры, виджеты, тайлмапы, аниматоры, скелеты, коллайдеры, ИИ-агенты, разрушаемые, шарниры. |

Они питают и [панель Statistics](#3-панель-statistics), и
[Advanced Profiler](#4-панель-advanced-profiler), и каждая из них сохраняется покадрово
внутри записанного [трейса](#41-запись-трейсов).

### 2.2 Скоупы и тайминг рендер-пассов

Точный тайминг CPU обеспечивают **скоупы**. Код движка (и ваш) инструментирован макросами
скоупов, которые замеряют блок и вкладываются по глубине вызовов:

* `ICE_PROFILE_SCOPE("Name")` — замерить именованный блок.
* `ICE_PROFILE_FUNCTION()` — замерить текущую функцию.

Скоупы накапливают покадровое число вызовов и длительности, а также формируют
иерархический **список событий**, используемый для отрисовки CPU-**флейм-таймлайна**.
Движок инструментирован повсюду (обновление, рендер, физика, пост-обработка, тени и т. д.).
Lua-скрипты могут добавлять свои скоупы через `ProfileBegin` / `ProfileEnd` /
`ProfileScope` (см. [5.5](#55-управление-профайлером-из-lua)).

Работа GPU замеряется по **рендер-пассам** через **`RenderPassProfiler`**, который
обрамляет пассы макросом `ICE_RENDER_PASS("Name")` и использует тройную буферизацию
GPU-таймер-запросов, чтобы сообщать время **CPU и GPU** на пасс (например, тени,
освещение, пост-обработка, UI). Пассы **вкладываются** по глубине вызова (с отступом в
панели): время родителя *включает* дочерние, а строка **Total** суммирует только пассы
верхнего уровня, поэтому двойного учёта нет. Записывается до **64 пассов на кадр**, а
результаты читаются на **два кадра позже**, чтобы не останавливать GPU — поэтому время GPU
пассов слегка отстаёт от CPU-чисел. Захват пассов можно полностью отключить на
[вкладке Render Passes](#47-вкладка-render-passes).

### 2.3 Интеграция с Tracy

Движок интегрирует кадровый профайлер **Tracy**. При сборке с включённым Tracy те же
макросы скоупов и рендер-пассов эмитят зоны Tracy, так что вы можете подключить внешнее
приложение **Tracy** для наносекундного, многокадрового, многопоточного анализа. Мьютексы
внутри профайлера тоже Tracy-aware, поэтому конкуренция за блокировки видна в том же
захвате.

Tracy компилируется в:

* **редакторские** сборки (всегда) и
* **Debug**-сборки игры.

Релизные сборки игры поставляются с **выключенным** Tracy для нулевых накладных расходов.
Кроме того, Tracy **недоступен на Web, Android и iOS** независимо от конфигурации;
используйте его на Windows, Linux или macOS. Инструментированная сборка ничего не собирает,
пока приложение Tracy реально не подключится, так что пока ничего не подключено, Tracy
внутри сборки не стоит вам ничего.

### 2.4 Датчики температуры

Температуры CPU/GPU берутся из фонового сэмплера, который опрашивает датчики примерно раз
в **1,5 секунды** в отдельном потоке, поэтому их чтение ничего не стоит кадровому потоку.
Панель всегда показывает, *какой* источник ответил:

| Платформа | Источники CPU (побеждает первый ответивший) | Источники GPU |
| --------- | ------------------------------------------- | ------------- |
| **Windows** | `LHM/HTTP` → `LibreHWMon` → `OpenHWMon` → `PDH` → `WMI/Perf` → `TempProbe` → `ACPI` | `NVML` → `NVAPI` → `D3DKMT` → `LibreHWMon` → `LHM/HTTP` → `OpenHWMon` |
| **Linux** | `hwmon` (coretemp / k10temp / zenpower…) → `thermal_zone` | `NVML` → `hwmon` → `thermal_zone` |
| **macOS** | Недоступно — Apple не предоставляет публичного thermal API | Недоступно (по той же причине) |

Большинство машин на Windows **не** сообщают температуру CPU «из коробки». При первой
неудаче движок пишет подсказку в лог: установите **LibreHardwareMonitor**, запустите его
от администратора, включите *Options → Remote Web Server* (порт по умолчанию 8085) и
перезапустите движок — после этого он автоматически определяется по
`http://127.0.0.1:8085/data.json` без прав администратора на стороне движка. Температура
GPU на NVIDIA обычно работает без всего этого (NVML/NVAPI).

## 3. Панель Statistics

**`Window → Stats`** открывает панель с заголовком **Statistics** — лёгкий, всегда
доступный обзор текущей сцены и рендерера, организованный в сворачиваемые секции.

### 3.1 General (Общее)

* **FPS** (с цветовой индикацией: зелёный ≥ 60, жёлтый ≥ 30, красный ниже) и **Frame
  Time** (мс) со скользящим **графиком времени кадра**.
* **Total Entities** (всего сущностей) плюс живая разбивка по типам: спрайты, флипбуки,
  аудио, FX, источники света, прожекторы, камеры, виджеты, тайлмапы, аниматоры, скелеты,
  риджидбоди, коллайдеры, столкновения спрайтов, скрипты, ИИ, разрушаемые, шарниры.
* Для **выбранной сущности**: её тег и **UUID**.

> Разбивка считает *инстансы*, а не сущности: одна сущность с четырьмя спрайт-инстансами
> даёт четыре спрайта. Поэтому суммы по типам могут превышать **Total Entities**.

### 3.2 Texture Atlas (Атлас текстур)

* **Страницы** атласа, **размер** страницы, размер **макс. спрайта** и число
  **упакованных** текстур.
* **Standalone textures** (текстуры вне атласа).
* Полосы **заполненности** на каждую страницу (с цветовой индикацией: зелёный < 50 %,
  жёлтый < 85 %, оранжевый выше) и число **регионов**, упакованных в страницу, чтобы
  заметить давление на атлас.

### 3.3 Renderer (Рендерер)

* **Вызовы отрисовки**, **число квадов**, производные счётчики **вершин/индексов**.
* **Активные частицы** и **активные эмиттеры**.
* **Активное аудио** — воспроизводящиеся в данный момент голоса.
* **Шаг физики (мс)** и, когда существует физический мир, полные счётчики **Box2D** (тела,
  шейпы, контакты, шарниры, острова, высота дерева), число **рабочих потоков** физики и
  профиль физики (step / collide / solve, мс).
* **Сборщик мусора Lua** — размер (КБ) с графиком и показатель скорости аллокаций (КБ/с,
  с цветовой индикацией: зелёный до 10 КБ/с, жёлтый до 50, оранжевый выше) — бесценно для
  выявления «дёрганья» памяти скриптами.
* **Тени** — строка состояния **ON/OFF** (тени считаются включёнными, только если система
  теней инициализирована, освещение в режиме *Lit*, тени включены и хотя бы один источник
  их отбрасывает), тенеотбрасыватели, рёбра, источники света, отбрасывающие тени,
  состояние направленной тени, разрешение карты теней и — при включённом **Show Shadow
  Maps** — полоса **превью карт теней** по источникам (слот направленного света выделен).

### 3.4 Отладочная визуализация

Секция **Debug** переключает отладочную отрисовку во вьюпорте (это визуальные подсказки, не
часть игры). Те же флаги читаются и пишутся из Lua по имени — см.
[5.5](#55-управление-профайлером-из-lua):

* **Базовые:** коллайдеры, нав-сетка, маркеры сущностей, радиус света, дальность аудио,
  фрустум камеры, шарниры, контакты физики, спящие тела, векторы скоростей, сетка
  тайлмапа, границы FX, границы виджетов, цвет по Z-глубине, режим wireframe, заморозка
  отсечения (freeze culling).
* **Продвинутые:** карты теней, рёбра теней, тепловая карта света, тепловая карта
  нав-сетки, оверлей состояния ИИ, восприятие ИИ, пути ИИ.

## 4. Панель Advanced Profiler

**`Tools → Profiler (Tracy)`** открывает панель с заголовком **Profiler** («Advanced
Profiler»). Это глубокий инструмент производительности: вкладки, запись, история и
экспорт. В меню **View** доступны **Show Graphs**, **Show Engine Stats** и
**Pause Updates** (замораживает скользящие графики, не останавливая движок).

Вкладки: **Overview · CPU · Memory · GPU · Engine · Trace History · Render Passes.**
Вкладка **Engine** присутствует только при включённом *Show Engine Stats*.

Элементы управления трейсами расположены над вкладками и видны на любой вкладке.

### 4.1 Запись трейсов

**Трейс** — это записанный прогон множества кадров, который можно анализировать офлайн.

* Введите **имя трейса** и нажмите **Start Trace**; появятся красный индикатор **[REC]** и
  живой счётчик кадров. Нажмите **Stop Trace** для завершения. Если оставить имя пустым,
  трейс будет назван `Trace_ГГГГММДД_ЧЧММСС`; недопустимые в именах файлов символы
  заменяются на `_`, а при совпадении имени добавляется числовой суффикс.
* При остановке трейс сводится (среднее/мин/макс время кадра, перцентили **P95/P99**,
  среднее FPS/CPU/GPU, средняя и пиковая RAM, средняя VRAM, статистика по скоупам, кадры
  со спайками), **автоматически записывается на диск** и кладётся в **Trace History**
  (20 последних).
* Каждый кадр трейса хранит полный список событий скоупов, список рендер-пассов и все
  счётчики сцены — именно это делает возможными офлайн-таймлайн и сравнение кадров.
* Трейсы можно запускать и останавливать из игрового кода; см.
  [5.5](#55-управление-профайлером-из-lua).

### 4.2 Вкладка Overview

Живая панель: общая оценка **Performance** (Excellent ≥ 60 FPS / Good 30–60 / Poor < 30)
плюс **FPS**, **Frame Time**, **CPU Usage**, **GPU Frame Time**, **RAM Usage** (текущая /
всего, с пиком), **VRAM Usage** (отслеживаемая / всего, с пиком), **CPU/GPU Temperature**
с именами источников и ключевые счётчики рендера (вызовы отрисовки, квады, сущности).
Каждое значение раскрашено по бюджету.

При включённом **Show Graphs** рисуется скользящий график времени кадра (с наложенными
текущими FPS/мс), а при доступном GPU-тайминге — график времени GPU.

Ниже графиков Overview повторяет две вещи, которые обычно нужны с одного взгляда:

* **CPU Scope Breakdown** — **8 самых горячих скоупов** последнего кадра цветными полосами
  со временем и числом вызовов.
* **Render Passes** — пассы последнего кадра парами полос CPU (синяя) / GPU (оранжевая), а
  в заголовке — суммы CPU и GPU.

### 4.3 Вкладка CPU

* **Cores** — число физических / логических процессоров и, когда читается, тактовая
  частота в ГГц.
* **CPU Usage** (%) и **CPU Temperature** с именем источника.
* При **Show Graphs**: график загрузки CPU (0–100 %) и, при наличии датчика, график
  температуры CPU.
* **CPU Scope Breakdown** — таблица скоупов текущего кадра со **временем** и **числом
  вызовов**, с цветовой индикацией (зелёный < 2 мс, жёлтый < 8 мс, красный выше).

Глубокий анализ скоупов — флейм-таймлайн, статистика скоупов, спайки и сравнение кадров —
находится на [вкладке Trace History](#48-вкладка-trace-history--таймлайн-сравнение-кадров-и-трейсов),
потому что требует записанного трейса.

### 4.4 Вкладка Memory

Системная **RAM** (текущая / всего, пиковая, с полосой прогресса и графиком) и
**Video RAM (VRAM)** (отслеживаемая / всего, пиковая, с полосой прогресса и графиком),
плюс текущее **число GPU-аллокаций** — чтобы следить за утечками и ростом за сессию или
трейс.

Цифры VRAM берутся из собственного **трекера VRAM** движка (каждая текстура, буфер и
рендер-таргет, выделенные через RHI), а не от драйвера, поэтому измеряют *ваше*
потребление, а не всей системы.

### 4.5 Вкладка GPU

* Строка состояния с именем **GPU-таймера активного бэкенда** (например, timer queries
  OpenGL, таймстампы Vulkan) и его доступностью.
* **Время кадра GPU** с эквивалентным «GPU-bound» FPS, плюс **вызовы отрисовки** и
  **квады**.
* **Температура GPU** с источником и, при включённых графиках, графиком температуры.
* Блок **VRAM** (отслеживаемая / всего, пиковая, число аллокаций) с полосой прогресса.
* При **Show Graphs**: графики времени GPU, вызовов отрисовки и VRAM.

Тайминг GPU опирается на таймер-запросы драйвера; когда они недоступны, панель это
сообщает, а значение показывается как `N/A` — CPU-скоупы, память и счётчики продолжают
работать.

### 4.6 Вкладка Engine

Счётчики уровня движка из метрик сцены профайлера (сущности, спрайты, вызовы
отрисовки, квады, физические тела, активные скрипты и разбивка по компонентам), плюс блок
**Resource Manager**: число загруженных **текстур** и **шейдеров**, отслеживаемая VRAM,
пиковая VRAM и число GPU-аллокаций. Дополняет панель Statistics единым видом,
сфокусированным на профайлинге.

### 4.7 Вкладка Render Passes

Тайминг по рендер-пассам из `RenderPassProfiler`:

* **Enabled** — включает/выключает захват пассов (и его GPU-запросы).
* **Bar Chart** — переключает графические полосы CPU/GPU над таблицей.
* Итоги **CPU** и **GPU** по всем пассам верхнего уровня.
* Столбчатая диаграмма всех пассов (CPU синим, GPU оранжевым) с легендой и отступами по
  глубине вложенности.
* **Render Graph Metrics** — по строке на каждый граф рендеринга, построенный в этом кадре
  (движок строит граф *сцены* и граф *пост-обработки*; см.
  [Графика → Граф рендеринга](Graphics-RU-DOC.md#3-граф-рендеринга)) с миллисекундами
  **Compile** и **Execute**, числом **Passes**, **Skipped** (пропущенных) и **Reordered**
  (переупорядоченных) пассов и колонкой **Validation** (зелёное `OK` либо число ошибок — с
  пометкой *strict*, если граф работает в строгом режиме валидации). Именно здесь видно,
  что пасс пропускается или переупорядочивается вопреки ожиданиям.
* Точная **таблица** всех пассов с миллисекундами CPU и GPU (три знака после запятой) и
  строкой **Total**.

Это самый быстрый способ найти, какая стадия рендеринга дорога. Пассы, не выдающие работу
на GPU, показывают `---` в колонке GPU.

### 4.8 Вкладка Trace History — таймлайн, сравнение кадров и трейсов

Перечисляет записанные трейсы с их сводками и содержит весь офлайн-анализ.

**Compare Traces (сравнение трейсов).** Выберите трейс **A** и трейс **B** в двух
выпадающих списках сверху и получите таблицу «бок о бок» по **Avg Frame Time**,
**Avg FPS**, **Avg CPU**, **Avg GPU Time**, **Avg RAM** и **Avg VRAM** с процентной
колонкой **Diff**, окрашенной по тому, улучшение это или регресс. Самая быстрая проверка
«до/после» для оптимизации.

**Детали трейса.** Разверните трейс, чтобы увидеть среднее/мин/макс время кадра, P95/P99,
среднее FPS/CPU/GPU, среднюю и пиковую RAM, среднюю VRAM, число обнаруженных кадров со
спайками и путь файла, в который он сохранён. Далее две кнопки: **View in Timeline**
(разворачивает анализ ниже) и **Delete Trace** (убирает трейс из истории *и* удаляет его
файл на диске).

Открытие трейса в таймлайне даёт:

* **Фильтр скоупов** — введите подстроку; совпадающие блоки во флейм-графе обводятся
  жёлтым, остальные притухают. Маленькая **X** очищает фильтр.
* **Полоса кадров** — все кадры трейса цветными столбиками (зелёный < 16,67 мс, жёлтый
  < 33,33 мс, красный выше) с опорными линиями 60 FPS и 30 FPS. Наведите для времени и FPS
  кадра, кликните для выбора или переключайтесь клавишами **←/→**. Выбранный кадр
  подсвечен.
* **Заголовок кадра** — `Frame n / всего | мс | FPS`, плюс красная метка **[SPIKE]**, если
  кадр занял больше двойного среднего по трейсу.
* **Timeline (флейм-граф)** — вложенные события скоупов выбранного кадра на миллисекундной
  линейке с зелёной отметкой на 16,67 мс. При наведении на блок показываются его **время**,
  **% от кадра** и **глубина**. Масштаб — колесом мыши (0,5×–20×) или слайдером **Zoom**
  (0,5×–10×), кнопка **Reset** возвращает 1×. Если у кадра есть время GPU, оно рисуется
  зелёной полосой под строками CPU.
* **Render Passes** — таблица пассов выбранного кадра (CPU / GPU мс, с отступами по
  глубине) со строкой **Total**, суммирующей только пассы верхнего уровня.
* **Frame Comparison (Frame Diff)** — кнопками **A** и **B** закрепите текущий выбранный
  кадр в соответствующем слоте, затем сравните времена скоупов бок о бок со столбцом
  **Diff** (красный — медленнее, зелёный — быстрее); первой строкой идёт само время кадра.
  **Clear** сбрасывает оба слота.
* **Scope Statistics** — время **Avg / Min / Max / Total**, число вызовов и число
  **спайков** на скоуп, с сортировкой по любой колонке. **Спайк** скоупа означает кадр, в
  котором *этот скоуп* превысил двойное собственное среднее — это намеренно отличается от
  спайка *кадра* (кадр дольше двойного среднего **времени кадра**). В заголовке показано,
  сколько кадровых спайков содержит трейс, и есть кнопка **Go to spike**, перескакивающая
  таймлайн к следующему.

### 4.9 Где лежат трейсы и экспорт Chrome trace

Остановленные трейсы записываются в JSON в **`Tools/Helpers/Profiler/`** внутри
записываемого пути движка — это папка вашего проекта, если она доступна для записи
(обычный случай редактора), иначе пользовательская директория данных
(`%APPDATA%\IceBoxEngine\game` на Windows, `~/.local/share/IceBoxEngine/game` на Linux).
Один файл на трейс, названный по имени трейса.

При старте профайлер **загружает трейсы обратно из этой папки** — 20 самых свежих по
времени изменения — поэтому Trace History переживает перезапуск редактора. Удаление трейса
в панели удаляет и его файл.

Файл трейса содержит сводку, статистику по скоупам, индексы кадров со спайками и все
захваченные кадры (время кадра/GPU, FPS, CPU, температуры, RAM/VRAM, дерево событий
скоупов, список рендер-пассов и все счётчики сцены).

**Экспорт Chrome trace** создаёт JSON формата Chrome Trace Event (`chrome://tracing`,
совместим с Perfetto) с именованными дорожками `CPU Main`, `GPU`, дорожкой счётчиков и
метаданными движка. Он доступен как **вызов из скриптов, а не кнопка в панели** — вызовите
`SaveChromeTrace()` из Lua (см. [5.5](#55-управление-профайлером-из-lua)); без аргумента
он пишет в ту же папку профайлера, а на Web дополнительно инициирует скачивание в браузере.

## 5. Профайлинг и отладка в рантайме

Профайлинг не ограничен редактором — движок поставляет те же средства в игру, чтобы вы
могли диагностировать производительность на реальных устройствах и в готовых сборках.

### 5.1 Экранная отладка (DebugScreen)

**`DebugScreen`** — это система экранного текста движка времени выполнения (по сути,
«печать на экран»). Из игрового кода вы можете:

* **Печатать** временные или постоянные сообщения на экран (с цветом, длительностью,
  масштабом и опциональным целочисленным ключом, чтобы сообщение обновлялось на месте, а
  не накапливалось) — `PrintScreen` / `PrintScreenEx`, убирается через
  `RemoveScreenMessage` / `ClearScreenMessages`.
* **Печатать текст в мировом пространстве**, привязанный к мировой позиции (отлично для
  подписей сущностей, отображения состояния ИИ, чисел урона и т. п.) — `DrawWorldText` /
  `DrawWorldTextEx`, убирается через `RemoveWorldText` / `ClearWorldText`. Мировой текст за
  пределами видимого вьюпорта отсекается.

Временем жизни управляет аргумент длительности: **положительная** длительность истекает
через столько секунд, плавно гаснув в последние полсекунды; **`0`** означает *только этот
кадр* (вызывайте каждый кадр для живого показания — именно поэтому у `DrawWorldText` это
значение по умолчанию); **отрицательная** длительность делает сообщение постоянным, пока вы
не уберёте его по ключу или не очистите список. Всю систему можно глобально выключить через
`SetScreenEnabled(false)`
(`IsScreenEnabled()` читает состояние). Текст рисуется **и во вьюпорте редактора, и в
самостоятельном рантайме**, поэтому то, что вы видите при тестировании, видят и игроки.

Это основной способ выводить живые значения (FPS, счётчики, состояние) внутри работающей
сборки. (Точки входа из скриптов — в [Lua API](LuaAPI-RU-DOC.md).)

### 5.2 Консоль разработчика (Developer Console)

Движок включает выпадающую **консоль разработчика (Developer Console)**,
доступную в рантайме и в редакторе:

* Переключается настраиваемой клавишей — по умолчанию **`` ` ``** (тильда/ёлочка); выезжает
  поверх игры.
* **Автодополнение** команд (Tab), **история** ввода (↑/↓), прокрутка, выделение текста и
  цветной вывод (info / warning / error / success / command).
* Выполняет зарегистрированные **команды** и **CVar'ы** для живой инспекции и подкрутки во
  время работы игры; команды и переменные регистрируются и из C++, и из Lua. См.
  [Lua API → Console](LuaAPI-RU-DOC.md#60-console--консоль-разработчика-и-система-команд).

### 5.3 Оверлей профайлера в рантайме

Самостоятельные **Debug**-сборки игры несут встроенный текстовый оверлей, который рисует
профайлер прямо на экране — без редактора и внешних инструментов. Он выводится слева
сверху и показывает:

* Состояние отладочной отрисовки коллайдеров / маркеров сущностей / нав-сетки и идёт ли
  запись трейса.
* **FPS** и время кадра (с цветовой индикацией), **CPU %**, **RAM** (текущая + пик),
  **VRAM** и **GPU**-время, если есть GPU-таймер.
* **Engine Stats** — сущности, спрайты, вызовы отрисовки, квады, физические тела, скрипты,
  тайлмапы, источники света, прожекторы, FX, аудио, виджеты, камеры, флипбуки, аниматоры,
  коллайдеры, ИИ, разрушаемые, шарниры.
* **Hot Scopes** — 8 самых дорогих скоупов последнего кадра со временем и числом вызовов.
* **Render Passes** — первые 6 пассов с миллисекундами CPU (и GPU).
* Строку `[TRACING: n frames]`, пока идёт запись трейса.

Оверлей **выключен по умолчанию** и **не имеет встроенной горячей клавиши** — назначьте её
сами и вызывайте `ToggleDebugProfiler()`. Он существует только в сборках, скомпилированных
как **Debug** *без* редактора; в Release переключатель — безвредная пустышка.

### 5.4 Сетевой профайлер

Второй оверлей, рисуемый в правой части того же экрана, покрывает мультиплеерный трафик.
Движок инструментирует все пути отправки/приёма (ENet на десктопе, WebSocket на Web) и
агрегирует данные по типам сообщений. Оверлей показывает:

* **State** (Offline / Server / Client-Connected / Connecting / Reconnecting) и число
  игроков.
* **Ping** (с цветовой индикацией: зелёный < 80 мс, жёлтый < 200 мс, красный выше).
* **Bandwidth per second** — TX/RX в КБ/с и пакетов/с.
* **Totals** — отправленные/принятые байты и пакеты в человекочитаемом виде.
* Разбивку по **типам сообщений**, отсортированную по суммарному трафику, — так неожиданно
  «болтливый» тип сообщения сразу заметен.

Как и оверлей профайлера, он существует только в Debug-рантайме и не имеет клавиши по
умолчанию — переключайте его через `NetworkProfiler.Toggle()`. Те же счётчики в любой
момент читаются из Lua (со скользящей 120-секундной историей и вызовом `SaveReport`), а
редактор показывает их живыми графиками в панели **Менеджер сети** — см.
[Редактор → Менеджер сети](Editor-RU-DOC.md#11-менеджер-сети-enet) и
[Lua API → Network](LuaAPI-RU-DOC.md#32-network--мультиплеер-сеть).

### 5.5 Управление профайлером из Lua

Всё, что делают элементы управления трейсами в редакторе, доступно игровому коду — именно
так профайлят на телефоне или в готовой сборке:

| Вызов | Что делает |
| ----- | ---------- |
| `StartProfilerTrace([name])` → `bool` | Начать запись трейса. Возвращает `false`, если запись уже идёт. |
| `StopProfilerTrace()` | Остановить и свести текущий трейс (и записать его на диск). |
| `IsProfilerTracing()` → `bool` | Идёт ли запись трейса. |
| `SaveChromeTrace([filename])` → `bool` | Экспортировать последний завершённый трейс — либо текущий, либо снимок одного кадра, если трейсов нет — в JSON формата Chrome Trace Event. |
| `ProfileBegin(name)` / `ProfileEnd(name)` | Открыть и закрыть пользовательский CPU-скоуп по имени. |
| `ProfileScope(name, fn)` → `any` | Выполнить `fn` внутри скоупа и вернуть его результат, даже если он упал с ошибкой. |
| `ToggleDebugProfiler()` / `GetDebugProfilerVisible()` | Переключить / прочитать [оверлей профайлера](#53-оверлей-профайлера-в-рантайме). |
| `NetworkProfiler.Toggle()` / `NetworkProfiler.IsVisible()` | То же для [сетевого оверлея](#54-сетевой-профайлер). |
| `GetDebugFlag(name)` / `SetDebugFlag(name, v)` / `ToggleDebugFlag(name)` | Прочитать/записать любой отладочный флаг вьюпорта по имени (`"ShowColliders"`, `"WireframeMode"`, …). |
| `GetDebugFlagNames()` / `ClearDebugFlags()` | Список всех допустимых имён флагов / сброс всех флагов. |
| `IsDebugBuild()` → `bool` | Скомпилирован ли этот бинарник как Debug. |

Пользовательские скоупы появляются в CPU-разбивке, флейм-таймлайне и Tracy ровно так же,
как движковые. Полные сигнатуры и примеры — в
[Lua API → Debug](LuaAPI-RU-DOC.md#29-debug--отладка).

### 5.6 Профайлинг готовой сборки

* **Debug**-сборки игры под десктоп включают инструментацию **Tracy** — подключите внешнее
  приложение Tracy, чтобы профайлить реальный поставляемый бинарник на целевой машине.
  (На Web/Android/iOS Tracy недоступен; там используйте оверлеи и трейсы.)
* Debug-сборки также несут оверлеи [профайлера](#53-оверлей-профайлера-в-рантайме) и
  [сети](#54-сетевой-профайлер), умеют записывать трейсы и экспортировать Chrome trace из
  Lua — это практичный способ профайлинга на телефоне.
* Системы **Statistics**/**Profiler** — часть ядра движка, так что те же метрики можно
  вычислять в рантайме и выводить через `DebugScreen` или собственный UI.
* **Release**-сборки отключают Tracy и оба оверлея ради нулевых накладных расходов;
  используйте `DebugScreen`/консоль и собственные внутриигровые показания для лёгких
  проверок в рантайме.

# Часть II — Сборка игр

## 6. Конвейер сборки кратко

Сборка превращает ваш проект (рантайм движка + ваш `Content/`) в самостоятельное
приложение для выбранной платформы. Общий поток:

```
Диалог Build Game (настройки)
        │
        ▼
[опц.] Подготовка ассетов ──► Saved/Cooked/<tag>/Content   (mobile/web)
        │
        ▼
Консолидация редиректоров
        │
        ▼
Запуск платформенного скрипта  (Tools/BuildSystem/BuildGame/build_<platform>.bat|.sh)
        │   → CMake + тулчейн компилируют IceBoxRuntime с вашим Content (встроен/по ссылке)
        ▼
Сбор результата → в выбранную папку вывода
        │
        ├─ копирование рантайма/бандла, game.json, LICENSE, THIRD_PARTY_NOTICES, ThirdPartyLicenses/
        ├─ копирование Content/ (на десктопе — подготовленного), включённых Plugins/ и Mods/ (по Packages)
        ├─ копирование и правка Config/Engine.json, Plugins.json, Mods.json, CollisionGroups.json
        ├─ [опц.] Упаковка Content → Content.icepak (zstd, опц. разбиение)
        ├─ [macOS] переподпись, затем .dmg / .pkg / нотаризация
        ├─ [опц.] Генерация game_manifest.json (SHA-256 каждого файла)
        └─ [опц.] Создание инсталлятора (NSIS / .deb)
```

Сам диалог не компилирует код — он собирает настройки, запускает нужный **скрипт сборки**
асинхронно (чтобы редактор оставался отзывчивым, с анимированной полосой прогресса и
кнопкой **Stop**), а затем выполняет шаги пост-сборочной упаковки. Вывод скрипта построчно
стримится в лог редактора с префиксом `[build]`.

## 7. Диалог Build Game

Откройте его из меню **`Tools → Build Game…`**; он показывает модальное окно
**Build Game Settings**. Диалог адаптируется к выбранной **Target Platform**, показывая
только релевантные секции, и все настройки запоминаются в конфиге редактора между
сессиями (кроме паролей).

### 7.1 Общие настройки

| Настройка | Значение |
| --------- | -------- |
| **Target Platform** | Windows, Linux, Android, Web, macOS, iOS. Остальная часть диалога меняется под выбор. |
| **Configuration** | **Debug** или **Release** (см. [7.2](#72-конфигурация-debug-vs-release)). |
| **Game Name** | Имя продукта; используется для имени исполняемого файла/бандла и метаданных инсталлятора. |
| **Icon Path** | Иконка приложения (`.png`/`.ico`/`.jpg`/`.jpeg`/`.bmp`); PNG автоматически конвертируется в платформенные форматы иконок. |
| **Output Path** | Папка для готовой сборки — подпапка `<Output>/<GameName>` создаётся и **очищается** в начале каждой сборки. Кнопка **…** открывает системный выбор папки. |
| **Version Name / Version Code** | Человекочитаемая строка версии (например, `1.2.0`) и целочисленный номер сборки (минимум 1). |
| **Publisher** | Имя студии/издателя, используется в инсталляторах и метаданных. |
| **Include Plugins** | *(Packages)* Поставлять плагины, отмеченные в `Tools → Plugins & Mods`. Включено по умолчанию; действует на все шесть платформ. Плагины с `"EditorOnly": true` не поставляются никогда, независимо от этой опции. |
| **Include Mods** | *(Packages)* Поставлять моды, отмеченные в `Tools → Plugins & Mods`. Включено по умолчанию; действует на все шесть платформ. |

Диалог не начнёт сборку с пустым **Game Name** или **Output Path**. Во время сборки все
настройки заблокированы, кнопка **Build** превращается в **Stop**, а отмена стирает
недописанную папку вывода. **Esc** закрывает диалог, когда ничего не выполняется.

> Замечание о кросс-платформенности: на не-Windows хосте выбор **Windows** запускает
> кросс-компиляцию через MinGW; **macOS/iOS** можно собрать только на хосте macOS
> (Windows-`.bat`-заглушки для этих платформ предлагают запустить `.sh` на Mac).

### 7.2 Конфигурация: Debug vs Release

* **Debug** — символы, без оптимизаций, с вкомпилированным профайлингом **Tracy** (на
  десктопе), плюс оверлеи [профайлера](#53-оверлей-профайлера-в-рантайме) и
  [сетевого профайлера](#54-сетевой-профайлер). Лучше всего для диагностики падений и
  производительности на целевой платформе.
* **Release** — оптимизировано, Tracy и отладочные оверлеи выключены. Поставляйте именно
  это.

> **Debug из установленного движка.** Два пункта выше описывают сборку **Debug** из полного
> дерева исходников движка. У движка, установленного из дистрибутивного установщика,
> исходников нет — вместо них он линкует заранее собранное ядро движка, и Build Game сам
> выбирает нужное:
>
> | Вы выбираете | Что получает игра |
> |---|---|
> | **Release** | Оптимизировано, никакой отладочной оснастки. Это и поставляйте. |
> | **Debug** | Оптимизировано **и** полностью инструментировано: **Tracy**, [оверлей профайлера](#53-оверлей-профайлера-в-рантайме), [оверлей сетевого профайлера](#54-сетевой-профайлер), `IsDebugBuild()` возвращает `true`, плюс полные отладочные символы и нестрипнутый бинарник. |
>
> То есть сборка **Debug** из установленного движка оставляет код самого движка
> оптимизированным — для вас это незаметно: дистрибутив не содержит исходников движка, по
> которым можно было бы шагать отладчиком, а логика вашей игры в любом случае живёт в
> Lua/Python. Все отладочные возможности и полные символы для вашей сборки при этом на месте.

### 7.3 Crash Reporter (отчёты о падениях)

Секция каждой платформы содержит поле **Crash Report URL**. Когда поставляемая игра
падает, движок пишет полный отчёт (стек, информация о системе, данные о графике и хвост
лога) в `Saved/CrashReports/` на машине игрока и показывает диалог падения. Если указать
контролируемую вами конечную точку `http://` или `https://`, из этого диалога отчёт можно
отправить в один клик.

* Значение проверяется: всё, что не является `http(s)`-URL, игнорируется с
  предупреждением в логе сборки.
* Оно записывается в **`game.json`** сборки как `CrashReportUrl`. На **iOS** поле вместо
  этого передаётся скрипту сборки (`--crash-report-url`), и CMake вшивает его в `game.json`
  внутри подписанного `.app`.
* Оставьте поле пустым — и упакованная игра ничего никуда не отправляет: отчёты остаются на
  диске игрока.

> **Свой приёмник писать не обязательно.** С движком идёт готовый и бесплатный:
> в [`Tools/CrashReport/`](../../Tools/CrashReport/README.md) лежит веб-приложение на
> Google Apps Script, которое принимает загрузку и пересылает каждый отчёт вам на почту
> письмом с приложенным файлом. Разверните его, вставьте полученный URL в **Crash Report
> URL** — и отправка в один клик работает на всех платформах.

## 8. Настройки по платформам

Каждая платформа открывает свою секцию в дополнение к общим настройкам. Выбранный здесь
графический бэкенд записывается в `Config/Engine.json` сборки и выбирается во время
выполнения (с откатами).

### 8.1 Windows

* **Вывод:** исполняемый файл `.exe` с DLL.
* **Графический API:** **OpenGL 4.6** (по умолчанию), **OpenGL 3.3** (совместим с GPU
  примерно с 2010 г.) или **Vulkan** (откатывается к OpenGL 4.6/3.3, если недоступен).
* **Архитектура:** **x64** (по умолчанию) или **x86** (32-бит, для максимальной
  совместимости со старыми системами). 64-битный редактор собирает обе; 32-битный
  редактор зафиксирован на **x86**, и переключатель отключён, потому что 32-битный
  тулчейн не может выпускать 64-битные бинарники.
* Поддерживает опции **Distribution** (манифест, упаковка контента, инсталлятор) — см.
  [Раздел 10](#10-дистрибуция-манифест-упаковка-и-инсталляторы).

### 8.2 Linux

* **Вывод:** исполняемый файл Linux (ELF).
* **Графический API:** OpenGL 4.6 / OpenGL 3.3 / Vulkan (как в Windows).
* **Архитектура:** x64 / x86 — правило хоста то же, что в Windows: 64-битный редактор
  собирает обе, 32-битный — только x86. Для сборки x86 нужен 32-битный multilib-тулчейн
  (`gcc-multilib` / `g++-multilib`) и триплет vcpkg `x86-linux`.
* Поддерживает опции **Distribution**, включая инсталлятор **.deb**.

### 8.3 Android

* **Вывод:** пакет `.apk` или **App Bundle** `.aab` для Google Play.
* **ABI:** `arm64-v8a` (по умолчанию, 64-битный ARM), `armeabi-v7a` (32-битный ARM,
  старые устройства), `x86_64` (64-битные эмуляторы) или `x86` (32-битные устаревшие
  эмуляторы).
* **Графический API:** **OpenGL ES 3.2** или **Vulkan** (откатывается к GLES 3.2/3.0).
* **Ориентация:** Landscape / Portrait / Auto.
* **Package Name** (например, `com.studio.game`), **Min SDK** / **Target SDK** (24–36;
  Min зажимается так, чтобы никогда не превышать Target), **Version Code** /
  **Version Name**, **Publisher**.
* **Сервисы** (переключатели, встроенные в шаблон Android): **Ads** (AdMob App ID),
  **In-App Purchases**, **Play Games** (App ID), **Consent**, **In-App Review**,
  **Notifications**, **Bluetooth**, **Firebase**, **Saved Games**.
* **Extra Permissions** (кастомные разрешения Android).
* **Подпись:** путь к keystore, пароль keystore, key alias, пароль ключа (для подписи
  релиза; иначе без подписи/с debug-подписью). Пароли **никогда не сохраняются в конфиг
  редактора** — вводите их каждую сессию — и передаются скрипту сборки через
  короткоживущие временные файлы (`--keystore-pass-file` / `--key-pass-file`, удаляются по
  завершении сборки), а не в командной строке, поэтому они не утекают в список процессов.
  Кнопка **Создать хранилище ключей…** создаёт новое релизное хранилище через `keytool`
  (JDK) — сначала введите пароль keystore (от 6 символов); key alias по умолчанию берётся
  из названия игры, файл — `<проект>/Keystore/<GameName>.jks`, имя сертификата берётся из
  **Publisher** (или названия игры), а если файл уже существует, генерация отклоняется,
  чтобы существующий ключ нельзя было перезаписать. Релизный ключ нужен для публикации в
  Google Play и выпуска совместимых обновлений; он **не** убирает предупреждение
  «установка из неизвестных источников» при ручной установке любого APK. Храните созданный
  keystore и его пароль в надёжном месте с резервной копией — тем же ключом должно
  подписываться каждое будущее обновление.

### 8.4 Web

* **Вывод:** `.html` + `.wasm` + файлы данных (Emscripten).
* **Рендерер:** **Auto (WebGPU → WebGL 2.0)**, **WebGPU** (Chrome/Edge 113+, Safari 18+)
  или **WebGL 2.0** (максимальная совместимость). Шейдеры транслируются в **WGSL** в
  браузере при загрузке.
* **Web-опции:** поддержка **Web3**, режим **main-loop**, **pthreads** (многопоточность,
  требует cross-origin isolation).
* Version Name / Version Code / Publisher.
* Текущий уровень передаётся как **стартовая сцена**; контент встраивается в `.data`
  Emscripten (так что `Engine.json`/`Plugins.json`/`Mods.json` предзагружаются, а не
  копируются россыпью). Моды на Web не поддерживаются.
* Шаг упаковки также копирует рядом с `.html` сгенерированные сопутствующие файлы
  (`.js`, `.wasm`, `.data`), а также `favicon.png` и `apple-touch-icon.png`, если сборка
  их создала.

### 8.5 macOS

* **Вывод:** бандл `.app` (собирается на Mac с Xcode).
* **Графический API:** **Metal через ANGLE** (OpenGL ES 3.0, транслируемый в Metal) или
  **Metal через MoltenVK** (Vulkan на Metal).
* **Архитектура:** **x86_64** (Intel) или **arm64** (Apple Silicon).
* **Deployment Target** (зажимается до минимума движка), **Bundle ID**, **Category**
  приложения.
* **Подпись:** codesign identity, **Hardened Runtime**, **Notarize** (+ профиль нотариуса
  в связке ключей).
* **Дистрибуция:** опциональный drag-install **`.dmg`** и опциональный настоящий
  **инсталлятор `.pkg`** (со своим **Installer Signing Identity**, а также **Homepage** и
  **Contact Email**) — см. [10.3](#103-инсталляторы).
* Всё, что нужно игре (`game.json`, `Content/`, `Config/`, `Plugins/`, `Mods/`,
  `LICENSE.txt`, `THIRD_PARTY_NOTICES.txt`, `ThirdPartyLicenses/`), укладывается в
  `Contents/Resources/` внутри бандла. Поскольку укладка данных ломает подпись, сделанную
  при сборке, редактор **переподписывает готовый бандл** — вашей identity (добавляя
  доверенную метку времени, а при Hardened Runtime — стандартные entitlements) либо
  ad-hoc, если identity не задана.

### 8.6 iOS

* **Вывод:** подписанный **`.ipa`** (через Xcode) или неподписанный бандл `.app`.
* **Графический API:** Metal через MoltenVK (Vulkan на Metal).
* **Bundle ID**, **Development Team**, **Code-Sign Identity**, **Provisioning Profile**,
  **Deployment Target** (зажимается до минимума движка).
* **Destination:** Device (`iphoneos`) или Simulator (`iphonesimulator`).
* **Ориентация:** Landscape / Portrait / All; **Requires Fullscreen**.
* **Метод экспорта** (при создании IPA): development / ad-hoc / app-store / enterprise.
  Выбор симулятора принудительно включает `--no-ipa` — сборки под симулятор нельзя
  упаковать в IPA.
* Опциональные ассеты **Entitlements**, **App Icon** (`.png`/`.appiconset`),
  **Launch Screen** (`.storyboard`).
* **Возможности:** Game Center, In-App Purchases, CloudKit, Push Notifications и
  **Multicast Networking**. Каждая включённая возможность подмешивается в файл
  `.entitlements`, которым подписывается сборка. Multicast Networking нужен, чтобы на
  iOS 14+ работал поиск игр в локальной сети через UDP-broadcast, и Apple должна
  одобрить этот entitlement для вашего Team ID, иначе профиль с ним не выдадут.
* **Info.plist / приватность:** **URL-схема диплинков** (регистрируется в
  `CFBundleURLTypes`, приходит в Lua API `DeepLinks`), **AdMob App ID**
  (`GADApplicationIdentifier`), **текст запроса локальной сети** (пишется всегда —
  сетевой мультиплеер по LAN требует его на iOS 14+), произвольные
  **доп. описания разрешений** (`NSCameraUsageDescription=Причина`, по одному в строке)
  и **Uses Non-Exempt Encryption** (`ITSAppUsesNonExemptEncryption`).
  `NSUserTrackingUsageDescription` и строка локальной сети объявляются автоматически;
  если указать любую из них в **доп. описаниях разрешений**, она заменит текст по
  умолчанию, а не продублирует ключ. Строка ATT не опциональна — iOS завершает
  приложение, вызвавшее `requestTrackingAuthorization` без неё, а именно это делают
  `Consent.ShowForm()` и `Permissions.Request("TRACKING")`.
* **Манифест приватности:** в каждый `.app` кладётся `PrivacyInfo.xcprivacy` с
  объявлением required-reason API, которые использует рантайм (времена файлов, место на
  диске, время загрузки системы, `NSUserDefaults`). Без него App Store Connect отклоняет
  загрузку с ITMS-91053. Свой `PrivacyInfo.xcprivacy` можно положить рядом с `Content/`
  проекта — проектный файл всегда побеждает движковый, поэтому при подключении SDK,
  собирающего данные, расширяйте его, а не боритесь с ним.
* **Реклама на iOS:** Google Mobile Ads SDK с движком не поставляется. Один раз выполните
  `Tools/BuildSystem/BuildEngine/fetch_googlemobileads.sh`, чтобы положить локально
  `GoogleMobileAds.xcframework`, затем включите **Ads & Attribution** и задайте AdMob App
  ID. С положенным SDK сборка его линкует и `Ads.*` начинает работать; без него эти
  вызовы остаются no-op. Пустой AdMob App ID при слинкованном SDK намеренно роняет
  конфигурацию, потому что SDK падает на старте без `GADApplicationIdentifier`.
* Бандл `.app` полностью самодостаточен: `game.json` (стартовая сцена, имя, версия,
  ориентация, URL отчётов о падениях), `Content/`, `Config/` (с зафиксированным бэкендом
  MoltenVK), включённые `Plugins/` и `Mods/` укладываются **до** подписи кода, поэтому
  готовый `.ipa` не требует пост-обработки — и по той же причине редактор намеренно
  пропускает на iOS свои копии сопутствующих файлов.

## 9. Подготовка ассетов (cooking)

Включите **Cook Assets**, чтобы перед упаковкой конвертировать сырые медиа в компактные,
удобные для рантайма формы — резко уменьшая размер сборки, при этом загрузчики времени
выполнения остаются неизменными. Настройки подготовки появляются в диалоге при включении.

| Медиа | Опции |
| ----- | ----- |
| **Texture Format** | **PassThrough** (копировать сырой PNG/JPG), **WebP** (с потерями, ~80% меньше), **KTX2 UASTC** (GPU-сжатие, высокое качество), **KTX2 ETC1S** (GPU-сжатие, компактно), **WebP Lossless**. Форматы с потерями используют общий **Quality** 1–100 (по умолчанию 80). |
| **Audio Format** | **PassThrough**, **Ogg Vorbis** или **Opus**, с **Bitrate** 32–320 кбит/с для вариантов с потерями (96 хорош для SFX, 128–192 для музыки). |
| **Video Format** | **PassThrough** или **VP9 (WebM)** с выбранным **CRF** (18 = высокое качество … 32 = меньше размер), с опциональными **max resolution** (Source/1080p/720p/480p), **max FPS** (Source/30/60), **strip audio** и битрейтом аудио 64–320 кбит/с. |
| **Font Mode** | **PassThrough**, **Subset** (только глифы, объявленные в сайдкарах шрифта) или **Auto-subset** (только глифы, фактически используемые в проекте). |
| **JSON Mode** | **PassThrough** или **Minify** (убрать пробелы из `.json` и сайдкаров `.ice_*`). |

**Защита от потерь:** когда выбран формат текстур с потерями, подготовщик кодирует каждую
текстуру, декодирует результат обратно и сравнивает с исходником. Если разница была бы
заметна — а именно это WebP с потерями и блочное GPU-сжатие делают с пиксель-артом с
резкими краями — такая текстура сохраняется без потерь, и подготовленная сборка совпадает
с неподготовленной пиксель в пиксель. Итоговая строка сообщает, сколько текстур было
**оставлено без потерь**, а каждая из них логируется с измеренной ошибкой. Переопределить
можно для каждой текстуры через **Compression** в сайдкаре (`Без потерь` — никогда не
сжимать, `Всегда сжимать` — пропустить проверку).

**Ограничения по платформам:** WebP-текстуры недоступны в рантайме **iOS** и **Web**, а
видео VP9 — на **iOS** (AVFoundation декодирует только H.264/HEVC); там принудительно
включается PassThrough. **KTX2** требует десктопного рантайма x86/x64 (Windows/Linux или
macOS Intel), потому что использует транскодер Basis Universal — на остальных целях
происходит откат к WebP, а где недоступен и WebP — к PassThrough. Диалог применяет всё это
автоматически: неподдерживаемые пункты скрываются или блокируются, оранжевая заметка
объясняет замену, а **ваш сохранённый выбор сохраняется**, поэтому при переключении обратно
на подходящую платформу он восстанавливается. Для Web-сборки с PassThrough-видео выводится
информационная заметка: исходники H.264/MP4 не воспроизведутся в сборках Chromium без
проприетарных кодеков (большинство браузеров под Linux), поэтому для переносимого
Web-видео выбирайте VP9.

Подготовщик **учитывает кэш** — кэш для конкретной сборки лежит в
`Saved/CookCache/<GameName>_<Platform>.json`, поэтому перекодируются только изменившиеся
входы, — работает в несколько **параллельных воркеров** (по умолчанию столько, сколько у
машины аппаратных потоков) и зеркалит удаления: файлы, исчезнувшие из источника, удаляются
из подготовленной папки. Итоговая строка лога сообщает счётчики
подготовлено / без изменений / из кэша / оставлено без потерь / ошибок и суммарную экономию
байт; **любая ошибка прерывает сборку**. Входными данными для подготовки являются
**сайдкары**, которые вы создаёте в Контент-браузере (sRGB/макс. размер текстур, диапазоны
глифов шрифтов и т. д.) — см. [Ассеты и Контент-браузер](Assets-RU-DOC.md).

> Для сборок **mobile/web** подготовка выполняется *перед* скриптом сборки, и
> подготовленная папка `Saved/Cooked/<tag>/Content` передаётся в сборку (так что
> подготовленные ассеты встраиваются). Поскольку эти цели встраивают весь корень проекта,
> подготовщик дополнительно укладывает рядом с подготовленным контентом `Config/`,
> `Plugins/`, `Mods/`, `LICENSE.txt` и файл `.iceproject`. Для **десктопа** подготовка
> выполняется на шаге упаковки, и в вывод копируется (и упаковывается) именно
> подготовленное дерево.

## 10. Дистрибуция: манифест, упаковка и инсталляторы

Для **Windows / Linux / macOS** секция **Distribution** предоставляет финальные опции
упаковки.

### 10.1 Манифест сборки

**Generate Manifest** пишет `game_manifest.json` рядом со сборкой, содержащий имя игры,
версию, дату сборки, конфигурацию, платформу, признак упакованности контента и запись для
**каждого файла** с его **SHA-256-хешем** и размером (плюс итоги). Полезно для выкладки в
сторы, патчинга и проверок целостности. Он генерируется *после* упаковки, поэтому описывает
то, что реально поставляется.

### 10.2 Упаковка контента (IcePak)

**Pack Content** упаковывает всё дерево `Content/` в единый архив **`Content.icepak`**,
уменьшая россыпь файлов и защищая ассеты от случайной модификации. Рантайм монтирует пак
через [IceVFS](Assets-RU-DOC.md#24-виртуальная-файловая-система-icevfs), так что загрузчики
не меняются.

| Опция | Значение |
| ----- | -------- |
| **Max Pak Size (MB)** | Разбить на `Content_0.icepak`, `Content_1.icepak`, … когда общий размер превышает это. `0` = один файл. |
| **IcePak Compression Level** | Уровень **zstd** **1–22**: 1 = быстрее всего, 3 = по умолчанию (сбалансировано), 19 = высокий (~10–15% меньше, медленно), 22 = максимум (очень медленно). |

Перед упаковкой редактор **разрешает редиректоры ассетов**: каждая ссылка в уложенном
контенте переписывается на финальный путь (с проходом по цепочкам редиректов), а
файлы-заглушки `.ice_redirect` удаляются — так что ничто в поставляемом паке от них не
зависит. После успешной записи пака **россыпная папка `Content/` удаляется**; если упаковка
не удалась, россыпные файлы сохраняются, поэтому неудачный пак никогда не даст сборку без
контента. На macOS пак кладётся внутрь `Contents/Resources/`.

**Формат IcePak:** простой индексированный архив (магия `ICEPAK02`, версия 2) с путём,
смещением, исходным и сжатым размерами на запись и флагом сжатия (zstd); файл, который не
сжимается, хранится «как есть». Паки можно монтировать слоями, так что патч/DLC-паки
перекрывают базовый контент.

### 10.3 Инсталляторы

**Create Installer** (Windows/Linux) создаёт полноценный инсталлятор с деинсталлятором и
регистрацией в системе, используя метаданные **Homepage** и **Contact Email**. Лучшая
найденная в папке вывода иконка (`.ico` > `.png` > `.bmp` > `.jpg`) и `LICENSE.txt`
проекта передаются скрипту автоматически:

* **Windows** — инсталлятор **NSIS** `.exe` (требует установленный NSIS). Вызывает
  `create_game_installer_windows.bat` (`.sh` на не-Windows хостах).
* **Linux** — пакет **`.deb`** (требует `dpkg-deb`; на Windows-хостах это идёт через WSL).
  Вызывает `create_game_installer_linux.*`. Игра ставится в `/opt/<Имя игры>`, запуск
  кладётся в `PATH` как `/usr/bin/<имя-пакета>`, пункт меню — в
  `/usr/share/applications`, иконка 256×256 — в тему hicolor, лицензия — в
  `/usr/share/doc/<имя-пакета>/copyright`. Имя пакета — имя игры, приведённое к
  допустимому в Debian виду (нижний регистр, `a-z0-9+.-`), а версия в control — версия
  сборки без ведущего `v`. Удаление пакета также стирает `/opt/<Имя игры>`, поэтому
  сейвы, записанные рядом с игрой, деинсталляцию не переживут.

Инсталлятор пишется **рядом** с папкой вывода —
`<Output>/<Name>-<version>-<Config>-Windows-<arch>-Setup.exe` или
`…-Linux-<arch>-Setup.deb`, — и после его успешного создания уложенная папка
`<Output>/<GameName>/` **удаляется**, потому что инсталлятор уже содержит всё. Если шаг
создания инсталлятора провалился, россыпная сборка остаётся на месте, и об этом пишется в
лог.

**Лимиты размера проверяются до упаковки.** Инсталлятор для **Windows** не может быть
больше **2 ГБ**, и ни один файл внутри него тоже не может достигать 2 ГБ. Скрипт сначала
измеряет папку игры, подбирает подходящий режим сжатия и — если не подходит ни один —
отказывается сразу, назвав слишком большой файл, вместо того чтобы упасть в середине
упаковки.

У пакетов **`.deb`** такого потолка нет, но они собираются через промежуточную копию,
поэтому скрипт проверяет, что на файловой системе для неё есть запас места: во многих
дистрибутивах `/tmp` — это `tmpfs` в оперативной памяти, и большой игрой его легко забить.
Переменная **`ICE_STAGING_ROOT`** позволяет перенести промежуточную копию в другое место.
Когда `.deb` собирается **с Windows-хоста** (через WSL), она намеренно делается в файловой
системе WSL, а не на `C:`, потому что примонтированный Windows-диск не может нести
POSIX-права, нужные пакету — поэтому в этом случае `ICE_STAGING_ROOT` должна указывать на
Linux-каталог, а не на путь внутри `/mnt/`:

```bash
export ICE_STAGING_ROOT=$HOME/.cache/icebox-stage
```

В любом случае уложенному дереву выставляются корректные для пакета владелец и права, так
что `.deb`, собранный на Windows, ничем не отличается от собранного на Linux.

У **macOS** свои две опции в секции macOS, применяемые после переподписи бандла:

* **Create .dmg** — drag-install образ диска, собираемый через `hdiutil`, содержащий `.app`
  и симлинк на `/Applications`, подписанный вашей identity, если она задана.
* **Create .pkg Installer** — настоящий инсталлятор, создаваемый
  `create_game_installer_macos.sh` (нужны Xcode Command Line Tools:
  `pkgbuild`/`productbuild`), который устанавливает игру в `/Applications`, показывает вашу
  лицензию и добавляет ярлык на рабочий стол. Пишется как
  `<Name>-<version>-<Config>-macOS-<arch>-Installer.pkg` и может подписываться
  **Installer Signing Identity**.
* **Notarize** отправляет **каждый** созданный артефакт (`.dmg`, `.pkg` или сам `.app`,
  если ни один не запрашивался) в `notarytool --wait` с вашим профилем нотариуса из связки
  ключей и при успехе прикрепляет (staple) тикет.

## 11. Что происходит при нажатии Build

1. **Валидация** — имя игры и путь вывода должны быть заданы; папка вывода `<path>/<name>`
   очищается и создаётся заново.
2. **Имена скрипта и артефактов** выбираются под платформу (например, `build_windows.bat`,
   рантайм `IceBoxRuntime.exe`, файл игры `<Name>.exe`).
3. **Сборка аргументов** — все настройки диалога превращаются во флаги командной строки
   (см. [Раздел 12](#12-справочник-скриптов-сборки)); пароли keystore идут через временные
   файлы.
4. **Предварительная подготовка** (mobile/web, если включён Cook Assets) → папка
   подготовленного контента; при ошибке сборка прерывается.
5. **Консолидация редиректоров**, чтобы ссылки чисто разрешались в сборке.
6. **Запуск скрипта сборки** асинхронно — CMake конфигурирует и собирает `IceBoxRuntime` с
   вашим контентом; диалог показывает живую полосу прогресса и кнопку **Stop** и стримит
   вывод скрипта в лог.
7. **Сбор результата** — найти собранный рантайм (в `out/gamebuild/…` или в откате на
   пользовательский кэш **GameBuilds**) и скопировать его в вашу папку вывода как
   `<GameName>` (файл или бандл, с сохранением симлинков для бандлов Apple).
8. **Копирование юридических файлов** — `LICENSE.txt` проекта плюс движковые
   `THIRD_PARTY_NOTICES.txt` и `ThirdPartyLicenses/` (для macOS — также в
   `Contents/Resources/`).
9. **Укладка контента** — копирование `Content/` (на десктопе он здесь же и готовится),
   пропуская движковую папку `Examples`.
10. **Запись `game.json`** — имя игры, версия, стартовая сцена, конфигурация, платформа,
    имя файла иконки и URL отчётов о падениях. Пропускается на iOS, где CMake пишет его
    внутрь подписанного бандла.
11. **Копирование сопутствующих конфигов** — `Config/Engine.json` плюс `Plugins.json` /
    `Mods.json` / `CollisionGroups.json` (пропускается там, где они встроены: Web, Android,
    iOS; `Plugins.json` / `Mods.json` также пропускаются, когда соответствующая опция
    **Include** выключена).
12. **Укладка плагинов и модов** — копируются только записи, отмеченные включёнными в
    `Plugins.json` / `Mods.json`, отсеивается мусор сборки (`Source/`, `build/`, `out/`,
    `.git/`, `*.obj`, `*.pdb`, `CMakeLists.txt`, …), а сверху накладываются свежесобранные
    бинарники плагинов (`.dll`/`.so`/`.dylib` + `plugin.json`). Полностью пропускается,
    когда выключены **Include Plugins** / **Include Mods**, и для любого плагина, чей
    `plugin.json` объявляет `"EditorOnly": true`. Также пропускается там, где плагины
    линкуются статически (Web, iOS) или упаковываются Gradle (Android); моды на Web не
    поддерживаются.
13. **Правка `Config/Engine.json`** — выставляется `Rendering.RenderBackend` для выбранного
    API и удаляются секции `Editor` и `Network`, относящиеся только к редактору.
14. **Копирование зависимостей рантайма** — `.dll` для Windows / `.so` для Linux из вывода
    сборки (библиотеки Python и pybind исключаются), иконка приложения и `game_icon.ico`.
15. **Упаковка / подпись / манифест / инсталлятор** — согласно опциям Distribution и, на
    macOS, переподпись бандла с последующими `.dmg` / `.pkg` / нотаризацией.
16. **Завершение** — сообщить об успехе (или подчистить при отмене/ошибке).

### Параллельные задачи компиляции

Каждый скрипт сборки сам подбирает число задач при запуске, чтобы 24-ядерная рабочая
станция не простаивала, а ноутбук с 4 ГБ не уходил в своп. Значение определяется в таком
порядке:

1. Явный `--jobs <n>` в командной строке.
2. Стандартная переменная окружения `CMAKE_BUILD_PARALLEL_LEVEL`, если в ней положительное
   целое. Удобно для CI, где раннер сам знает свой лимит.
3. Автоматически: `min(логические ядра, всего ОЗУ в МБ / 1536)`, но не меньше `1`.

Слагаемое по памяти — это защита слабых машин: сборка движка требовательна к памяти,
поэтому машина с большим числом ядер и малой памятью иначе ушла бы в своп. Определение
работает на Windows, Linux и macOS и учитывает лимиты по CPU и памяти в контейнерах; если
определить не удалось, скрипты откатываются на `4` задачи.

Переменная `ICE_BUILD_MB_PER_JOB` меняет бюджет памяти на одну задачу (по умолчанию
`1536`, минимум `256`): уменьшите её, чтобы задействовать больше ядер, или увеличьте, если
сборке когда-нибудь не хватит памяти.

Сборка через **пресеты CMake**, а не через скрипты (`cmake --build --preset ...`, Visual
Studio, VS Code CMake Tools), использует вместо этого значение по умолчанию самого
генератора — задайте `CMAKE_BUILD_PARALLEL_LEVEL`, чтобы зафиксировать его.

**Что делает скрипт сборки** (пример Windows): инициализирует окружение MSVC
(`vcvarsall`), находит **vcpkg**, требует **CMake** + **Ninja**, конфигурирует движок с
`ICE_RUNTIME_BUILD=ON` (редактор и Python выключены), Tracy включён для Debug и выключен
для Release, и вашими опциями контента/версии/бэкенда, собирает цель `IceBoxRuntime` и
пишет результат в `out/gamebuild/Windows-<arch>-<config>/bin/Windows/IceBoxRuntime.exe`.

Графический бэкенд прописывается в `Config/Engine.json` сборки как
`Rendering.RenderBackend`:

| Значение | Бэкенд | Пишется для |
| -------- | ------ | ----------- |
| `0` | OpenGL 4.6 | Windows / Linux (по умолчанию) |
| `1` | WebGL 2.0 | Web (встроено, не правится) |
| `2` | OpenGL ES 3.2 | Android (встроено, не правится) |
| `3` | OpenGL 3.3 | Windows / Linux |
| `4` | Metal через ANGLE | macOS |
| `5` | Vulkan | Windows / Linux / Android |
| `6` | Metal через MoltenVK | macOS / iOS |

> Скрипты сборки также можно запускать **вручную** из терминала с этими флагами, что удобно
> для CI. Если корень движка только для чтения, сборки откатываются в пользовательский кэш
> (`%LOCALAPPDATA%\IceBoxEngine\GameBuilds` / `~/.cache/IceBoxEngine/GameBuilds`), и
> редактор при сборе результата тоже туда заглядывает.

| macOS | `out/gamebuild/macOS-<arch>-<config>/bin/macOS/IceBoxRuntime.app` |
| iOS | `out/gamebuild/iOS-arm64-<sdk>-<config>/bin/iOS/…` (`<sdk>` = `iphoneos` или `iphonesimulator`) |
| Web | `out/build/Web/bin/Web/<Name>-<version>-<config>-Web.html` |
| Android | `out/gamebuild/Android/project/app/build/outputs/apk(\|bundle)/<config>/app-<config>.apk\|.aab` |

Готовый продукт копируется в **выбранную вами Output Path** в `<Output>/<GameName>/`,
вместе с `game.json`, `LICENSE.txt`, `THIRD_PARTY_NOTICES.txt`, `ThirdPartyLicenses/`,
`Config/`, `Content/` (или `Content.icepak`), включёнными `Plugins/`, `Mods/` и
`game_manifest.json`, где применимо. По пути он переименовывается:

| Платформа | Итоговое имя файла |
| --------- | ------------------ |
| Windows / Linux | `<GameName>.exe` / `<GameName>` |
| macOS / iOS | `<GameName>.app` либо `<GameName>.ipa` при создании IPA |
| Android | `<GameName>-<version>-<Config>-Android-<abi>.apk` (или `.aab`) |
| Web | `<GameName>-<version>-<Config>-Web.html` + сопутствующие файлы |

Если промежуточный результат не найден в `out/`, проверяется пользовательский кэш
**GameBuilds**. Инсталляторы пишутся на уровень выше, рядом с папкой `<GameName>` — см.
[10.3](#103-инсталляторы).

## 14. Требования к тулчейнам

Вы собираете нативным тулчейном под каждую цель. Установите это на хосте сборки:

| Платформа | Необходимые инструменты |
| --------- | ----------------------- |
| **Windows** | Visual Studio (рабочая нагрузка C++ / MSVC), **vcpkg**, **CMake 4.3+**, **Ninja**. ImageMagick опционально (лучше PNG→ICO). NSIS для инсталляторов. |
| **Linux** | GCC/Clang, vcpkg, CMake 4.3+, Ninja. `dpkg-deb` для инсталляторов `.deb`. (Из Windows: кросс-компиляция MinGW, опционально через WSL для инсталляторов.) CMake из репозиториев Debian/Ubuntu — включая образы WSL2 — обычно старее 4.3; см. раздел Linux / WSL2 в `README.ru.md`. |
| **Android** | **Android SDK** (`ANDROID_HOME`), **NDK**, **Gradle** (через встроенный wrapper), **JDK** (JBR из Android Studio определяется автоматически; `keytool` берётся оттуда же), Android-триплеты vcpkg. |
| **Web** | **Emscripten SDK** (`EMSDK`, `emcc` в PATH). |
| **macOS / iOS** | Хост **macOS** с **Xcode** (и command-line tools — `pkgbuild`/`productbuild` для `.pkg`, `notarytool` для нотаризации) и vcpkg. Для iOS дополнительно нужны команда разработки / ассеты подписи для сборок под устройство и IPA. |

Первая сборка конфигурации также собирает сторонние зависимости через vcpkg, так что
ожидайте, что она займёт больше времени, чем последующие инкрементальные сборки.

# Часть III — DLC

## 15. Упаковка DLC

**DLC Packager** (**`Tools → DLC Packager`**, отдельный диалог) создаёт паки загружаемого
контента, которые монтируются поверх базовой игры во время выполнения.

| Поле | Значение |
| ---- | -------- |
| **DLC ID** | Уникальный идентификатор (например, `expansion01`). Обязателен — по нему называются все создаваемые файлы. |
| **DLC Name** | Отображаемое имя. Обязательно. |
| **DLC Version** | Версия этого DLC. |
| **Min Game Version** | Минимально требуемая версия базовой игры. |
| **Content Folder** | Папка ассетов DLC для упаковки; её путь становится **префиксом** контента внутри пака (показывается прямо под выбором). |
| **Output Path** | Куда записать DLC (по умолчанию — папка вывода сборки, `<Output Path>/<Game Name>`). |
| **Pack IcePak** | Упаковать как сжатый `.icepak` (с разбиением по **Max Pak Size** и тем же уровнем сжатия **zstd** 1–22) — или поставить **россыпью**. |

Кнопка **Package DLC** остаётся заблокированной, пока не заполнены ID, имя и существующая
папка контента.

Упаковка пишет в подпапку **`DLC/`** пути вывода: дескриптор `DLC/<DLC ID>.json` (id, имя,
версия, минимальная версия игры, префикс контента, число файлов, суммарный размер, признак
упаковки, список файлов) плюс либо `DLC/<DLC ID>.icepak` — разбитый на
`<DLC ID>_0.icepak`, `<DLC ID>_1.icepak`, … при заданном лимите размера — либо россыпные
файлы под префиксом контента.

Во время выполнения игра сканирует `DLC/` при старте: читается каждый дескриптор, DLC
помечается **установленным**, если его пак (а для россыпного DLC — папка контента)
действительно на месте, и каждый `.icepak` из `DLC/` монтируется **после** базовых паков, в
порядке имён файлов. Поскольку
[IceVFS](Assets-RU-DOC.md#24-виртуальная-файловая-система-icevfs) разрешает пути по
последним смонтированным слоям, контент DLC добавляется к контенту базовой игры — или может
его перекрывать. **Min Game Version** записывается в дескриптор и доступна скриптам, так что
игра может отказаться включать DLC на несовместимой сборке. Lua-сторона этого —
[`DLC.*`](LuaAPI-RU-DOC.md#42-dlc--дополнительный-контент).

## 17. FAQ и устранение проблем

**Диалог Build сообщает, что скрипт сборки не найден.**
Скрипты сборки лежат в `Tools/BuildSystem/BuildGame/`. Убедитесь, что вы собираете из
полного чекаута движка (диалог находит корень движка автоматически).

**Сборка macOS/iOS ничего не делает на Windows.**
Так и задумано — `.bat`-скрипты являются заглушками. Платформы Apple требуют хост macOS с
Xcode; запускайте `.sh`-скрипты там.

**Моя первая сборка очень медленная.**
Первая конфигурация собирает все сторонние библиотеки через vcpkg. Последующие сборки
инкрементальны и намного быстрее.

**Куда делась моя сборка?**
В `<Output Path>/<Game Name>/`. Промежуточная сборка — в `out/gamebuild/…` (или в
пользовательском кэше `GameBuilds`, если папка движка только для чтения). Если вы включили
**Create Installer**, эта папка удалена намеренно — инсталлятор лежит уровнем выше.

**Опции WebP/KTX2/VP9 неактивны или принудительно PassThrough.**
Эти форматы поддерживаются не каждым рантаймом: WebP недоступен на iOS/Web, VP9 — на iOS, а
KTX2 требует десктопного рантайма x86/x64 (он использует транскодер Basis Universal). Диалог
применяет допустимые комбинации по платформам, но сохраняет ваш выбор для целей, где формат
поддерживается.

**Как сделать сборку меньше?**
Включите **Cook Assets** (текстуры WebP/KTX2, аудио Vorbis/Opus, видео VP9, сабсеттинг
шрифтов, минификация JSON) и **Pack Content** с более высоким уровнем zstd. Задавайте
хорошие входные данные в сайдкарах (макс. размер текстур, диапазоны глифов шрифтов).

**Время GPU показывается как недоступное.**
Тайминг GPU требует поддержки таймер-запросов драйвером. Вкладка GPU называет бэкендный
таймер, который она пыталась использовать. CPU-скоупы, память и счётчики всё равно работают.

**Температура CPU на Windows показывается как «недоступно».**
Windows не предоставляет непривилегированного API теплового датчика CPU. Установите
LibreHardwareMonitor, запустите его от администратора, включите *Options → Remote Web
Server* (порт 8085) и перезапустите движок — см. [2.4](#24-датчики-температуры).

**Мои трейсы пропали / я хочу их заархивировать.**
Это обычные JSON-файлы в `Tools/Helpers/Profiler/` внутри записываемого пути движка. Панель
держит 20 последних; копируйте старые из этой папки, пока они не вытеснились, и помните, что
**Delete Trace** удаляет и файл.

**В панели Profiler нет кнопки экспорта Chrome trace.**
Верно — это вызов из скриптов. Используйте `SaveChromeTrace()` из Lua; см.
[4.9](#49-где-лежат-трейсы-и-экспорт-chrome-trace).

**Как профайлить реально поставляемую игру?**
Соберите **Debug**. На десктопе подключите внешнее приложение **Tracy**. На любой платформе
можно включить встроенный [оверлей профайлера](#53-оверлей-профайлера-в-рантайме), записать
трейсы из Lua и экспортировать Chrome trace, и/или выводить метрики через **DebugScreen**.

**Можно ли запускать сборки из CI / командной строки?**
Да — вызывайте скрипты `build_<platform>` напрямую с флагами из
[Раздела 12](#12-справочник-скриптов-сборки); `--jobs` и `--clean` там особенно полезны.

## Headless (выделенный сервер)

Любая обычная сборка игры одновременно является выделенным сервером. Запустите рантайм
с `--headless` (работает и `-headless`):

```bash
IceBoxRuntime --headless
```

Окно не создаётся, графический контекст не создаётся, аудиоустройство не открывается.
Движок выбирает **Null-бэкенд рендера**: каждый вызов RHI становится пустышкой, а ресурсы
получают фиктивные хэндлы — поэтому никакой подсистеме движка не нужен особый путь кода.
`Render()` пропускается целиком; всё остальное — скрипты, физика, анимация, скелеты и
тела костей рагдолла, ИИ, сеть — работает ровно так же, как с окном. Поэтому авторитетное
определение попаданий и компенсация лагов ведут себя идентично listen-серверу.

Что это даёт на практике:

- Процесс никогда не засыпает при потере фокуса, сервер может работать без присмотра сколько угодно.
- Системы частиц продолжают считаться, поэтому время жизни эффектов истекает, а не копится.
- Ограничитель кадров работает, сервер выдерживает темп, а не жжёт ядро.
- Детерминированные UUID и общий генератор случайных чисел делают роллбэк-сессии на сервере воспроизводимыми.
- CPU-скоупы, RAM и счётчики сцены продолжают собираться, поэтому трейсы и `NetworkProfiler`
  работают; только GPU-таймингу нечего измерять.

Требования: никаких сверх обычной сборки — не нужны ни GPU, ни дисплейный сервер, ни сессия
X11/Wayland на Linux. Запускается в контейнере.
