2. WHEN ANYTHING IS SENT AT ALL
--------------------------------------------------------------------------------

No personal data is transmitted automatically. Nothing about you, your machine
or your work leaves your computer unless you press a button.

There is one automatic outbound request, and it carries nothing about you: when
IceBox Updater starts, it asks our release manifest whether a newer version of
the engine exists. The request contains no license key, no device identifier,
no account, no file path and no usage data - it only asks for the list of
releases. Your IP address is visible to the receiving service as it is for any
HTTPS request; we do not record it. The manifest is served by a Google Apps
Script web app - the same recipient named in section 6. You can switch this
check off with "Check for updates on startup" in the updater, and still check
by hand with "Check for Updates".

When the editor, launcher or updater crashes, a report file is written to
    <application data folder>/Saved/CrashReports/
on your own machine, and a dialog appears asking whether you want to send it.

  * Nothing leaves your machine unless you press "Yes" / "Send Report".
  * The button is never pre-selected, pre-checked, or triggered on a timer.
  * Pressing "No" closes the application and leaves the file on your disk only.
  * If sending fails (no network, endpoint down), the report is queued and one
    retry is attempted on the next launch. Declining is not retried - a declined
    report is never queued.

There is no telemetry, analytics, usage tracking, advertising identifier, or
background reporting in the editor, launcher or updater. Besides crash reports
and the version check above, the only thing these tools ever transmit is the
one-time license activation check described in section 9, which happens when
you press "Activate" and never again.

--------------------------------------------------------------------------------
3. WHAT A CRASH REPORT CONTAINS
--------------------------------------------------------------------------------

The full report file is plain text. You can open and read it before deciding to
send it - the dialog shows you its exact location. It contains:

  Crash identification
    - Engine version and build configuration (Release/Debug)
    - Platform and CPU architecture
    - Local timestamp of the crash
    - Signal / exception type, fault address, crashing thread id
    - Process uptime

  Process context
    - Path to the executable
    - Working directory
    - Full command line the process was started with

  Device and system information
    - Operating system name, version and build
    - CPU model, core counts, clock speed
    - GPU model, driver version, video memory; active renderer backend
    - Total / available / used RAM
    - Motherboard, disk model, free disk space on the application's volume
    - Display resolution, refresh rate, colour depth
    - On mobile: device model, SoC, ABI, battery level, screen density,
      locale of the device
    - On Web: browser name and version, user agent string, screen size,
      WebGL renderer, page origin and path (query strings are stripped)

  Diagnostics
    - Stack trace of the crashing thread with module and, where available,
      source file and line
    - The application's own log for that session (up to 100 000 lines)
    - On Windows, a separate .dmp minidump is written NEXT TO the report but
      is NEVER uploaded. It stays on your disk.

--------------------------------------------------------------------------------
4. PERSONAL DATA, AND WHAT IS REMOVED BEFORE SENDING
--------------------------------------------------------------------------------

Most of the content above is technical information about a machine, not about a
person. The parts that can relate to an identifiable person are file system
paths, because on most systems a home directory embeds the operating system
account name.

Before a report is written to disk - and therefore before it can be sent,
attached to an email, or read by anyone - the engine rewrites account names in
paths to the literal placeholder <user>:

    C:\Users\Michael\Games\X\game.exe   ->  C:\Users\<user>\Games\X\game.exe
    /home/michael/games/x/game          ->  /home/<user>/games/x/game
    /Users/michael/Library/...          ->  /Users/<user>/Library/...

This is applied to the entire report, including the command line, the stack
trace and the session log. Shared, non-personal account folders (Public,
Default, All Users, Shared, root) are preserved because they identify nobody.

The redaction is best effort, not a guarantee. If you have typed personal data
into a project path, a file name, a command-line argument, or if your own code
logs personal data during the session, that content can still end up in the
report. Please read the file before sending it if this matters to you.

No account name, email address, licence key, IP-based identifier or advertising
identifier is deliberately collected into a crash report. Your IP address is
visible to the receiving endpoint as it is for any HTTPS request; it is not
stored in the report body.

5. WHY (LEGAL BASIS) AND FOR HOW LONG
--------------------------------------------------------------------------------

Purpose
    To diagnose and fix defects in IceBox Engine. Reports are read by the
    engine's maintainers only, and are used for no other purpose. They are not
    used for profiling, advertising, or automated decision-making.

Legal basis
    Your consent, GDPR Art. 6(1)(a), given by pressing "Send" in the crash
    dialog. You may withdraw consent at any time; withdrawal does not affect
    processing that already took place.

Retention
    Crash reports are deleted no later than 90 DAYS after receipt. Reports
    linked to an open defect may be retained until that defect is fixed and
    released, and are then deleted.

    Copies stored locally on your own machine are under your control. The engine
    keeps only the 15 most recent reports in Saved/CrashReports/ and prunes
    older ones automatically; you may delete the folder at any time.

The default receiving endpoint is a Google Apps Script web app that forwards

    Recipient:  Google LLC and Google Ireland Limited
                (Google Apps Script and Gmail)
    Location:   United States and other countries where Google operates
    Basis:      The endpoint runs on an ordinary Google account, governed by

                therefore not acting as our processor on this service: it
                handles what reaches the mailbox on its own terms rather than

                because it is the honest description of the arrangement, and
                because it is your decision whether to press Send.
    Google's privacy policy: https://policies.google.com/privacy

If you would rather that no report of yours passed through Google, simply do not

engine works exactly the same either way.

If you build IceBox Engine yourself and point
Source/Engine/Core/CrashReportConfig.h at your own endpoint, the recipient is

8. GAMES BUILT WITH ICEBOX ENGINE - READ THIS IF YOU SHIP A GAME
--------------------------------------------------------------------------------

A packaged game NEVER sends crash reports to IceBoxCrew Studio.

The engine's built-in endpoint and contact address are compiled into the editor,
launcher and updater only. They are compiled out of IceBoxRuntime and
IceBoxCore, which are what a packaged game is built from. A game with no
endpoint configured writes the report to the player's device and sends nothing,
anywhere.

If you enter an address in the Build panel's "Crash Report URL" field (stored as
"CrashReportUrl" in game.json), or add an optional "CrashReportEmail", then:

  * YOU become the data controller for your players' crash reports, not
    IceBoxCrew Studio. IceBoxCrew Studio never receives them and is not a
    recipient, a processor, or a joint controller.
  * You must disclose that collection in your own game's privacy policy, name
    the recipients and processors you use (for example Google, if you host the
    endpoint on Apps Script - and note that an ordinary Google account carries
    no data processing agreement, as section 6 explains), state a retention
    period, and provide a contact for data subject requests. Sections 3 to 7 of
    this document are a usable starting point.
  * On iOS you must additionally declare crash data collection in your app's
    PrivacyInfo.xcprivacy. The template shipped with the engine declares
    NSPrivacyCollectedDataTypes as empty, which is correct only while no
    endpoint is configured. Once you configure one, add
    NSPrivacyCollectedDataTypeCrashData, or App Store review will reject the
    build.
  * On Android and Google Play you must reflect crash data collection in the
    Data safety form.
  * The <user> redaction described in section 4 applies to your players'
    reports as well, but it is best effort and does not by itself relieve you
    of the obligations above.

9. LICENSE ACTIVATION
--------------------------------------------------------------------------------

When the editor, launcher or updater is built with an activation endpoint
configured, pressing "Activate" on the activation screen sends one HTTPS request
to that endpoint. This is the only moment it happens:

  * Nothing is sent while you are just typing, pasting or reading the screen.
  * Nothing is sent after the activation succeeds. The engine does not re-check
    the license later, on a timer, or at any launch.
  * A build with no endpoint configured never sends anything at all and verifies
    the key entirely on your own machine.

What the request contains

    - the license key text you entered, and the key id inside it
    - the key set id of the build
    - a Device ID: a 10-byte keyed BLAKE2b hash of one machine identifier
      (Windows MachineGuid, macOS platform UUID, Linux /etc/machine-id, or the
      system volume identifier when none of those is readable). It is a hash,
      not the identifier itself, and it cannot be reversed back into it
    - the key's policy (device-locked, single-machine or shared)
    - the engine version, the platform name (Windows, macOS or Linux), a random
      one-off number that ties the answer to this request, and a UTC timestamp

No account name, user name, host name, email address, file path, hardware serial
number, or IP-based identifier is placed in the request. Your IP address is
visible to the receiving endpoint as it is for any HTTPS request; it is not
stored in the activation record.

What is stored

    Key id, Device ID, policy, edition, expiry date, first and last activation
    time, an activation counter, the engine version and the platform name, in a
    spreadsheet controlled by IceBoxCrew Studio. Refused attempts are recorded
    the same way, with the reason, so that a leaked key can be spotted and
    revoked.

Why (legal basis)

    Performance of the licence contract, GDPR Art. 6(1)(b): the record is what
    makes a single-machine key single-machine, and it is the only way a revoked
    key can be stopped without shipping a new build. Preventing licence fraud is
    additionally a legitimate interest, GDPR Art. 6(1)(f). Unlike a crash
    report, this check is not optional - it is part of delivering the licence -
    so it does not rest on consent.

Retention

    For as long as the licence exists, plus up to 12 months, after which the
    record is deleted.

Who else sees it

    Recipient:  Google LLC and Google Ireland Limited
                (Google Apps Script and Google Sheets)
    Location:   United States and other countries where Google operates
    Basis:      the same arrangement described in section 6 - an ordinary
                Google account under Google's own terms, with no data
                processing agreement behind it, so Google is not acting as our
                processor here either.

If you would rather not have an activation record on Google's infrastructure,
write to us before you activate and we will issue you a device-locked key
instead, at no cost. A device-locked key is verified on your own machine, against
the signature inside the key and the machine it was issued for, and it activates
whether or not our endpoint answers - so it also works with that endpoint
blocked, with the machine offline, and after our service one day stops existing.
The editor still attempts the single request described above when it can reach
the network; if that request does not get through, your activation succeeds all
the same and no record of it reaches us or Google - the only record is the one
on your own disk, which is yours. The only practical difference from an ordinary
key is that a device-locked key is tied to the machine you tell us about, so
replacing that machine means asking us for a new one.

Your rights under section 7 apply to activation records as well. Because a
record carries no account identifier, quote your Key ID and Device ID - both are
shown on the launcher's About tab and on the activation screen - when you write
to iceboxcrew057@gmail.com.

A packaged game NEVER performs a license activation check. The licensing module
is compiled into the editor, the launcher and the updater only; it is not part
of IceBoxRuntime or IceBoxCore, which are what a packaged game is built from.
